# 转写质量问题:诊断与改进方案

## 一、问题拆成三类,性质完全不同

| # | 现象 | 例子 | 性质 | 修法 |
|---|---|---|---|---|
| 1 | **同音字/术语未纠正** | `坚立视觉`(计算机视觉)、`二差数`(二叉树)、`像机`(相机) | **后处理缺失** | 接上已有的 LLM 纠错 |
| 2 | **口音导致听错** | 教师口音下的声学识别错误 | **模型能力** | 换模型 |
| 3 | **专有名词不在词表** | 人名、课程特有术语 | 两者都要 | 热词 + 纠错 |

`坚立视觉` 出现 8 次、`像机` 8 次 —— **同一错误重复出现是问题 1 的典型特征**,
模型每次都在同一个音上出错,而这正是"上下文纠错"最擅长处理的。

---

## 二、问题 1:接上已有的纠错(改动小、收益直接)

### 现状

`src-core/src/llm/prompt.rs:346` 里 `term_correction_prompt` 已写好:

```
你是一个中文语音转写校对助手。请修正转写文本中的错别字与术语错误。

严格约束:
1. 只做纠错,不改写句子 —— 不要润色、不要合并或拆分句子、不要调整语序。
2. 不要删除任何内容,包括口语重复和语气词。
3. 不要添加任何新内容,不要补充解释。
4. 拿不准的地方保持原样,宁可不改。
5. 只输出修正后的文本,不要任何说明文字。

参考术语表(可能出现的正确写法):{glossary}
```

**但没有任何地方调用它。** 所有转写产物(`transcript.md/json/srt`、工程目录里的副本)
都是原始输出。

### 要做的

1. 在管线里加一个**纠错阶段**,位于转写之后、说话人区分之前(或之后)
2. 保留一份原始转写,纠错结果另存 —— 用户要能对比
3. 缓存纠错结果(同样按内容哈希)
4. 按段纠错而不是整篇:整篇超过上下文要 map-reduce,且会丢失段落边界的对应关系

### 关键约束

- **时间戳不能乱。** 纠错只改文字,不改分段。所以按段纠错、逐段替换 `text`,
  `start_ms`/`end_ms` 保持不动。
- **要能回退。** 保留原始转写,界面给一个开关。
- **术语表要能长。** 现在 `--term` 走 `initial_prompt`(热词),对 Whisper 效果很弱;
  改成同时进纠错 prompt 才有效。

## 三、问题 2:换模型(收益大但改动也大)

### 当前配置的问题

用的是 `large-v3-turbo`。它是**蒸馏版**,为了速度牺牲了精度。而:

- 你的场景是**两小时课堂录音**,不是实时字幕 —— 速度没那么关键
- 实测 2h18m 用 turbo 转录 6 分钟(0.04x 实时),换 full large-v3 大约 4 倍慢
  → 约 25 分钟。**可以接受。**

### 候选方案

| 方案 | 优势 | 代价 |
|---|---|---|
| **whisper large-v3(非 turbo)** | 直接换文件,零代码改动 | 慢约 4 倍;精度提升有限 |
| **SenseVoice** | 官方称中文/粤语**明显优于 Whisper**;非自回归,比 Whisper-Large 快 15 倍 | 需要新增一个引擎适配 |
| **FireRedASR / Qwen3-ASR** | 同为中文优化 | 同上 |
| **在线 API**(阿里云百炼等) | 中文口语/方言最强 | 要联网、按量付费、音频出机器 |

### SenseVoice 的具体可行性

它有 **GGUF 版 + llama.cpp 运行时**,形态和 whisper.cpp 一样:

```
llama-funasr-sensevoice -m ./gguf/sensevoice-small-f16.gguf \
    --vad ./gguf/fsmn-vad.gguf -a audio.wav
```

这**完全契合现有架构** —— 我们的 `WhisperCppSidecar` 就是"跑一个外部 exe 读输出"。
换成 SenseVoice 相当于再加一个 sidecar 实现,后端切换机制不用动。

另外它有**神经网络热词增强**(`SenseVoiceSmall_hotword`),针对问题 3 比
Whisper 的 `initial_prompt` 有效得多。

### 但我不建议直接换,应该先测

**我无法判断 SenseVoice 在你这个具体录音上是否更好。** 官方 benchmark 用的是
AISHELL / WenetSpeech 这类标准普通话数据,而你的痛点是**口音**。

正确做法:
1. 从你那个 2h18m 录音里截几段有代表性的(口音重、术语密)
2. 用 whisper large-v3 / SenseVoice 各跑一遍
3. **逐字对比**再决定

这个对比我可以做,但需要先装 SenseVoice 的运行时(或者用 sherpa-onnx 的
SenseVoice 支持 —— 我们已经有 sherpa-rs 依赖了)。

## 四、建议的顺序

1. **先接纠错**(问题 1)—— 改动小、立即见效、不需要新依赖。
   `坚立视觉`→`计算机视觉` 这类错误靠它就够了。
2. **再做 A/B 对比**(问题 2)—— 用真实片段测 SenseVoice vs large-v3,
   用数据决定要不要换,而不是靠 benchmark 宣传。
3. **最后才考虑在线 API** —— 只有在 1+2 都不够时才值得引入联网依赖和按量付费。

## 五、关于在线 API 的取舍

**会更好吗?** 中文口语场景下,阿里云百炼/FunASR 这类确实通常更强,
因为它们用大量中文电话/会议数据训练,对口音和口语更鲁棒。

**但代价是实质性的:**

- **音频要出机器。** 现在整个设计的前提是"音频不出本机,只发文字给 LLM"。
  引入在线 ASR 会打破这条 —— 这是产品定位的改变,不只是技术选择。
- **按量付费。** 两小时录音反复重跑(改参数、试术语表)成本会累积。
- **网络依赖。** 离线不可用。
- **长音频上传耗时。** 148 MB 传上去再等结果,可能比本地 CUDA 转录更慢。

**所以我的建议是:先榨干本地方案。** 如果接上纠错 + 换更强的本地模型之后
仍不满意,再考虑在线 —— 那时是有依据的决定,而不是猜测。
