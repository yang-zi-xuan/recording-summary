## 1. 项目定位与已确认决策

### 1.1 定位

**自用工具。** 这一定位直接决定了很多设计取舍:

| 因为是自用,所以 | 不做 |
|---|---|
| 用户是理性的,清楚自己在录什么 | 同意流程、隐私弹窗、免责声明 |
| 错误对用户显式可见(你认得出同事的声音) | 事前防护式确认对话框 |
| 只有一个用户,无并发写 | 协作协议、CRDT、实时合并 |
| 出问题可以随时改代码 | 过度的事务保护和版本迁移 |

**但有一类东西不能因为是自用就省掉 —— 工程上保证 "可逆性" 和 "错误可见性" 的机制。** 它们不是防护,是功能本身(详见 §8)。

### 1.2 已确认的技术决策

| # | 决策项 | 结论 | 关键理由 |
|---|---|---|---|
| 1 | 产品形态 | **桌面 GUI 应用** | — |
| 2 | 转写引擎 | **本地 whisper.cpp,多后端 + 运行时自动降级** | 不绑定单一 GPU 厂商,CPU-only 也能跑(见 §3) |
| 3 | 总结引擎 | **云端 LLM(先支持 DeepSeek)** | 只发文字不发音频,成本可忽略 |
| 4 | 音频来源 | 文件导入 + 系统声音录制 + 麦克风 | 双轨独立采集是关键(见 §7.1) |
| 5 | 语言 | 中文为主(课堂/会议),兼顾英文 | 决定用 Whisper 而非 FunASR |
| 6 | 界面框架 | **Tauri 2 + React** | 包体小、内存低、Rust 原生推理无跨语言损耗 |
| 7 | 说话人区分 | **sherpa-onnx(纯 Rust)**,三档人数策略;后端同样可降级 | 避免拖 Python 运行时分发(见 §3.6) |
| 8 | 声纹档案 | **做**,简化版(无同意流程) | 让系统 "越用越准" |
| 9 | 场景判断 | **LLM 自动判断 + 一键切换兜底** | 两段式,低置信度显式提示 |
| 10 | 云端同步 | **WebDAV + 混合传输** | 文本走 WebDAV,音频交给 Seafile 客户端 |
| 11 | 同步范围 | 音频 + 文本 + 名字映射 | **声纹向量永不出本机** |
| 12 | 明文存储 | **不存**(API Key / WebDAV 密码) | 走 Windows 凭据管理器 |
| 13 | **硬件要求** | **无硬性要求** —— 从独显到纯 CPU 都能用,自动选档 | 见 §3 |

**关于决策 #2 的补充说明:** 初版方案按开发机(RTX 4060)写死为 CUDA。改为多后端后,**开发机仍走 CUDA(最快),但同一份代码能在无 GPU 机器上运行**。这不增加业务层复杂度 —— 因为 `Transcriber` 本来就是 trait(§4.2),后端只是它的一个实现细节。

### 1.3 被否决的方案(避免以后重新纠结)

| 方案 | 否决理由 |
|---|---|
| Electron + Node | 包体 100MB+,且反正要用 Rust/C++ 跑推理,Electron 换不来好处 |
| faster-whisper (Python) | 桌面客户端被迫打包 Python 运行时 |
| FunASR / SenseVoice 作为主引擎 | 中文短语音更准,但中英混合弱。你的场景中英夹杂是常态 |
| pyannote 做 diarization | 精度略好,但要拖 Python 分发 |
| 用自己的服务器做同步后端 | 对单人工具是过度投入,已有 WebDAV |
| 全部走 WebDAV 传音频 | 可行但需多写大文件续传逻辑,收益不明显 |
| **只支持 CUDA** | 绑死 NVIDIA;Vulkan 用同样的代码覆盖 AMD/Intel,没理由不做 |
| **只支持 CPU** | 浪费硬件;你的机器能 2 分钟跑完的活不该花 55 分钟 |

### 2.1 分层原则

```
│  src-tauri/        Tauri 2 桌面壳 + React 前端   │  ← 只管界面
├─────────────────────────────────────────────────┤
│  src-cli/          命令行入口                    │  ← 先跑通这个
├─────────────────────────────────────────────────┤
│  src-core/         全部业务逻辑                  │  ← 最值钱的部分
```

### 2.4 为什么转写走 sidecar 而不是 FFI

**决定:第一版用 sidecar(子进程调用 `whisper-cli.exe`),不直接 FFI 链接 `whisper-rs`。**

| | sidecar | FFI (whisper-rs) |
|---|---|---|
| 上手速度 | 快(官方预编译二进制) | 慢(要处理链接和构建配置) |
| 崩溃隔离 | ✅ 子进程崩了主程序没事 | ❌ 整个应用崩 |
| **多后端切换** | ✅ **换一个可执行文件即可** | ❌ 要重新编译链接 |
| 流式/细粒度控制 | 受限 | 完全可控 |
| 进度反馈 | 解析 stderr | 回调 |

**多后端这条是新增的决定性理由。** sidecar 模式下,"换后端"就只是换一个 exe 路径;FFI 模式下要维护多套构建配置。见 §3.5。

代价是有的:CPU 模式下 sidecar 的进程启动开销略高。但这个开销是秒级,面对 30 分钟以上的转写任务可以忽略。

## 3. 硬件适配与后端选择

> **设计目标:无硬性硬件要求。** 从独立显卡到纯 CPU 的老笔记本,同一份代码都要能跑 —— 只是速度和模型档位不同。
>
> 这**不增加业务层复杂度**,因为 `Transcriber` 本来就是 trait(§4.2),后端只是它的实现细节。

### 3.1 whisper.cpp 的后端现状

好消息:whisper.cpp 的后端覆盖面很广,**多后端是它的一等公民**,不需要我们自己写适配层。

| 后端 | 覆盖硬件 | 平台 | 说明 |
|---|---|---|---|
| **CUDA** | NVIDIA 独显 | Win / Linux | ★ 最快。**需自行编译**(官方默认 Release 不带) |
| **Vulkan** | **AMD / Intel / NVIDIA 通用** | Win / Linux / Android | ★ **跨厂商首选** —— 一个二进制覆盖三家 |
| **Metal** | Apple Silicon / AMD | macOS | 苹果平台用这个 |
| **ROCm / HIP** | AMD 独显 | Linux(Win 有限) | AMD 专用,生态比 Vulkan 窄 |
| **SYCL** | Intel 独显(Arc 等) | Win / Linux | Intel 专用 |
| **OpenCL** | 较老设备 | — | 兼容性兜底,性能一般 |
| **CPU** | **所有设备** | 全平台 | ★ **永远可用的兜底** |

**关键判断:Vulkan 是最有价值的 "第二后端"。** 因为你不可能为每家 GPU 厂商各打一个包,而 Vulkan 一个二进制就能覆盖 AMD、Intel、NVIDIA。有 [Windows 上的 CPU/GPU 与 CUDA/Vulkan 基准对比](https://starwhisper.ai/whisper-benchmark.html)可以参考实际差距。

**因此后端优先级(Windows):**

```
CUDA (NVIDIA,最快)  →  Vulkan (任何 GPU)  →  CPU (永远可用)
```

### 3.2 运行时探测与自动降级

**核心思路:不预设用户有什么硬件,启动时探测 + 自检,失败就往下退一级。**

```rust
// src-core/src/hardware/backend.rs

#[derive(Clone, Copy, Debug, Serialize, Deserialize, PartialEq)]
pub enum Backend {
    Cuda,
    Vulkan,
    Metal,
    Rocm,
    Sycl,
    OpenCl,
    Cpu,
}

#[derive(Clone, Copy, Debug, Serialize, Deserialize)]
pub enum BackendPref {
    Auto,            // 探测 + 自检,自动选
    Force(Backend),  // 用户手动指定
}

/// 本机实际可用的后端(按优先级排序)
pub fn available_backends() -> Vec<Backend>;

/// ★ 真正可靠的一步:跑一次微型转写验证
pub fn probe_works(backend: Backend) -> Result<ProbeResult, BackendError>;

pub struct ProbeResult {
    pub ok: bool,
    pub elapsed_ms: u64,
    pub rtf: f32,                    // 实时率:耗时 / 音频时长,越小越快
    pub device_name: Option<String>,
    pub error: Option<String>,
}
```

#### 探测手段

| 后端 | 探测方法 |
|---|---|
| CUDA | 检测 `nvidia-smi` 是否可执行 + 查询到的设备数 |
| Vulkan | `vulkaninfo` 或尝试加载 `vulkan-1.dll` |
| Metal | `cfg!(target_os = "macos")` + 芯片类型 |
| ROCm / SYCL | 各自运行时库是否存在 |
| CPU | **总是可用**,无需探测 |

#### ★ 为什么必须做 "微型转写自检"

**只用 `nvidia-smi` 判断是不够的。** 真实世界的失败模式包括:

- 驱动版本太老,不支持编译时用的 CUDA 版本
- CUDA 运行时库(`cudart` / `cublas`)缺失
- 显卡被远程桌面 / 虚拟机 / 多 GPU 环境屏蔽
- 显存不足(模型加载时才暴露)
- 集显 + 独显的笔记本,程序跑在错误的 GPU 上

**这些情况 `nvidia-smi` 都会说 "有 GPU",但转写会崩。**

所以正确做法是:**探测 → 用内置的 3 秒音频试转一次 → 通过才采用这个后端。** 整个自检通常 1~3 秒,但能避免 "启动就崩溃" 这种最差的体验。

#### 降级链

```rust
pub fn select_backend(pref: BackendPref) -> Backend {
    match pref {
        // 用户手动指定:尊重,但失败要明确报错(不静默降级)
        BackendPref::Force(b) => b,

        // 自动:按优先级探测,第一个通过自检的胜出
        BackendPref::Auto => [Backend::Cuda, Backend::Vulkan, Backend::Metal,
                              Backend::Rocm, Backend::Sycl, Backend::Cpu]
            .into_iter()
            .find(|b| available(*b)
                  && probe_works(*b).map(|r| r.ok).unwrap_or(false))
            .unwrap_or(Backend::Cpu),   // ★ CPU 永远兜底
    }
}
```

**注意 `Force` 分支:用户手动指定时不静默降级。** 如果他选了 CUDA 却没跑起来,要明确告诉他原因,而不是悄悄用 CPU 然后让他困惑 "为什么这么慢"。

### 3.3 模型自动分档(比后端选择更重要)

**无 GPU 时,真正的瓶颈是模型档位,不是后端。**

| 后端 | 推荐模型 | 预期速度 | 45 分钟音频 |
|---|---|---|---|
| **CUDA / Vulkan** | `large-v3-turbo`(int8) | 15~25× 实时 | **2~3 分钟** |
| **Vulkan(弱 GPU)** | `medium` | 3~6× 实时 | 8~15 分钟 |
| **CPU(现代多核)** | `base` / `small` | 0.5~1.5× 实时 | 30~90 分钟 |
| **CPU(老设备)** | `tiny` / `base` | 0.2~0.5× 实时 | **1.5~4 小时** ⚠️ |

```rust
// src-core/src/hardware/model_pick.rs
pub fn recommend_model(
    backend: Backend,
    vram_gb: Option<f32>,
    cores: usize,
) -> ModelTier;
```

**必须做到:探测到的硬件 → 自动选一个合理档位**,而不是让用户面对一堆模型名自己猜。

**UI 要如实呈现:**

```
⚙ 硬件加速:  CUDA · RTX 4060 Laptop          [更改]
📦 转写模型:  large-v3-turbo (1.6GB)          [更改]
   预计速度:  约 20× 实时(45 分钟音频约 2 分钟)
```

对比一下弱机器上应该显示什么:

```
⚙ 硬件加速:  CPU (未检测到可用 GPU)           [更改]
📦 转写模型:  small (466MB)                   [更改]
   预计速度:  约 0.8× 实时(45 分钟音频约 55 分钟)
   ⚠ 建议课前插电、别关盖子;可随时取消
```

> **★ 诚实提示比 "能跑" 更重要。** 纯 CPU 上跑一小时不是不能接受,但要提前让用户知道 —— 否则他会以为程序卡死了。

### 3.4 无 GPU 情况下的体验设计

CPU-only 会让转写从 "2 分钟" 变成 "1 小时",这会**改变整个交互设计**:

| 问题 | 设计对策 |
|---|---|
| 用户以为程序卡死 | **实时进度**(已处理音频时长 / 总时长),不是只有一个转圈 |
| 中途要关机 | **★ 支持取消,且已完成部分要保住** —— 见下 |
| 笔记本过热降频 | 检测到 CPU 模式时提示 "建议插电",并提供**线程数限制**选项 |
| 一次跑太多 | 提供**串行队列**,夜里批量跑 |
| 耗时不可预期 | 启动前先估时:"预计 55 分钟,是否继续?" |

#### ★ 分块转写 + 断点续传(CPU 模式下价值最大)

```
把长音频按 5~10 分钟切块(在句子边界切,见 §9.3)
  → 每块独立转写,完成后立即落盘
  → 中断后从最后一个完整块继续
```

**这块缓存的键就是现有设计(§4.8 的 `TranscriptCacheKey`)按块拆分。** 收益:

- 用户随时可以取消,不用怕白跑
- 断电/关机/崩溃后能从断点继续
- CUDA 模式下也受益(长会议不用一次跑完)

**这条在 CPU 模式下几乎是从 "不可用" 变成 "可用" 的差别。**

### 3.5 分发策略(打包体积问题)

**不能把所有后端都打进一个安装包。** 每个后端要带各自的运行时,而且 CUDA 版本需要匹配驱动。

| 方案 | 说明 | 取舍 |
|---|---|---|
| **① 只带 CPU** | 安装包最小,任何机器都能跑 | ✅ 兼容性最好 ❌ 慢 |
| **② CPU + Vulkan** | 覆盖绝大多数有 GPU 的机器 | ✅ **覆盖面/体积比最优** |
| **③ 全部带** | 安装包巨大 | ❌ 不推荐 |

**推荐组合:默认包带 CPU + Vulkan;CUDA 版作为可选下载。**

理由:

- **CPU 保证 "一定能跑"** —— 这是兼容性的底线,不能省
- **Vulkan 用很小的体积代价覆盖 AMD / Intel / NVIDIA** —— 性价比最高
- **CUDA 体积大且需匹配驱动版本**,让需要极致速度的用户按需下载

#### 后端按需下载(v1 可不做)

```
后端管理
  ✅ CPU(内置)
  ✅ Vulkan(内置)
  ⬇ CUDA 加速包(约 300MB)  [下载]   ← 检测到 NVIDIA 显卡时提示
```

**但第一版可以简化:开发机上直接编译 CUDA 版自己用,把多后端做成编译期可选。** 先把架构留出位置,再逐步补齐。

**sidecar 架构在这个方案下的优势就体现出来了:** "下载 CUDA 加速包" 只是解压一个目录 + 切换 exe 路径,不涉及任何重新编译。这正是 §2.4 选 sidecar 的原因之一。

### 3.6 其他组件也要能降级

**不只是转写要适配硬件,整条链路上的每个模型组件都要。**

| 组件 | 后端方案 | CPU 兜底 |
|---|---|---|
| **转写** | whisper.cpp:CUDA / Vulkan / Metal / CPU | ✅ 总是可用 |
| **说话人区分** | sherpa-onnx:CPU / CUDA / DirectML / CoreML | ✅ CPU 可用(慢但能跑) |
| **声纹嵌入** | 同上(共用模型) | ✅ 同上 |
| **音频解码** | ffmpeg(纯 CPU) | ✅ 无 GPU 依赖 |
| **重采样** | rubato(纯 CPU) | ✅ 无 GPU 依赖 |
| **总结** | 云端 LLM | ✅ **不需要本地算力** |

**关键设计:`asr` 和 `diarize` 各自独立探测和降级。**

不要做成 "一个全局 GPU 开关" —— 因为它们的依赖不同。可能出现的情况:

- 转写用 CUDA(whisper.cpp CUDA 版装好了)
- 但 diarization 走 CPU(sherpa-onnx 的 CUDA provider 没配)

**这完全可以接受,而且比 "一个开关" 更稳。** UI 上分别显示两行即可。

**还有一个好处:总结走云端意味着最耗算力的那一环彻底不依赖本地硬件。** 即使在一台纯 CPU 的旧笔记本上,你也能得到完整功能,只是转写慢。

### 3.7 硬件适配对照表

| 机器 | 后端 | 模型档位 | 45 分钟音频耗时 |
|---|---|---|---|
| **开发机**(i9-14900HX + RTX 4060 8GB) | **CUDA** | `large-v3-turbo` | **约 2~3 分钟** |
| 有独显的笔记本(AMD / Intel Arc) | Vulkan | `medium` | 8~15 分钟 |
| 核显笔记本 | Vulkan(可能不通过自检 → CPU) | `small` | 20~55 分钟 |
| 纯 CPU 老机器 | CPU | `base` | 30~90 分钟 |
| Apple Silicon | Metal | `large-v3-turbo` | 约 3~5 分钟 |

**这张表解释了为什么 §14.7 建议 "W2 之后先用手机录音跑真实课程"** —— 你在开发机上验证流程,而其他机器只在速度上不同,**功能完全一致**。

```rust
// src-core/src/store/cache.rs

pub struct TranscriptCacheKey {
    pub audio_hash: String,
    pub asr_model: String,
    pub backend: Backend,              // ★ 后端也进键
    pub diarize_enabled: bool,
    pub diarize_model: Option<String>,

    pub vad: bool,
    pub hotwords_version: u32,
    pub chunk_index: Option<u32>,      // ★ 分块转写的块号(见 §3.4)
}

pub struct EmbeddingCacheKey {
    pub audio_hash: String,
    pub seg_model: String,
    pub emb_model: String,
    pub backend: Backend,              // ★ 同上
}

pub trait Cache {
    fn get_transcript(&self, key: &TranscriptCacheKey) -> Result<Option<Transcript>>;
    fn put_transcript(&self, key: &TranscriptCacheKey, t: &Transcript) -> Result<()>;

    // ★ 声纹嵌入独立缓存 —— 让 "改人数重聚类" 变成秒级
    fn get_embeddings(&self, key: &EmbeddingCacheKey) -> Result<Option<EmbeddingSet>>;
    fn put_embeddings(&self, key: &EmbeddingCacheKey, e: &EmbeddingSet) -> Result<()>;
}
```

**★ `backend` 和 `chunk_index` 是本次新增的两个键。**

- **`backend` 必须进键** —— 同一个模型在 CPU 和 CUDA 下可能产生**细微不同的结果**(浮点累加顺序不同)。如果后端不参与缓存键,你会遇到"在 A 机器上转写、拷到 B 机器后结果对不上"的问题
- **`chunk_index` 支持分块缓存** —— CPU 模式下断点续传的基础(§3.4)

**注意缓存键里没有发言人名字。** 改名是展示层的事,不触发重新转写。这是刻意的设计(见 §8.3)。

## 5. 数据模型

### 5.1 核心设计:分享的是文件,不是数据库

**这是同步能不能简单实现的决定性选择。**

```
共享数据(文件形态,跨设备同步)         本地数据(数据库,不共享)
  transcript/ab/ab3f9c...json      SQLite:
  summary/ab/ab3f9c...md             session_index(索引与元数据)
  profiles.json                      speaker_embeddings(嵌入缓存)
  speaker_labels/*.json              audio_local_path(本机路径)
  manifest.json                      hardware_profile(★ 本机硬件探测结果)
```

**理由:**

- **文件形态天然可合并、可调试、可手动检查、可备份。** 你出问题能直接用记事本打开看
- **数据库只做本地缓存,可以随时删掉从文件重建** —— 于是**完全不需要处理数据库合并冲突**,这是同步系统里最麻烦的部分
- 文本很小:一节课的转写 JSON 约 200~500KB,500 节课也就 250MB

**因此:任何 "跨设备必须一致" 的数据,一律以文件为真相源。**

**★ `hardware_profile` 明确不进同步。** 每台机器的硬件不同,探测结果必须本机独立。(见 §3.2)

### 5.2 SQLite Schema(本地缓存)

```json

```

**`speaker_labels/<hash>.json`** —— 单独拆出来是为了**改名字不重写大文件**:


## 6. 转写输出格式规范

### 6.1 三层结构

```
① 存储层(唯一真相源)   Vec<Segment> —— 带时间戳、speaker_id、overlapped
② 派生层(展示用)       对话体 / 时间轴 / 纯文本
③ 导出层(srt/md/txt)  从 ①② 派生
```

**绝不要把 "带时间戳的文本" 当存储格式。** 理由:时间戳跳转、搜索定位、重新对齐说话人都需要结构化字段;而显示格式会反复改,字符串无法反推回结构。

### 6.2 三种视图

#### 视图 A:对话体(默认)

```
[00:00:03] 张老师:
今天我们要讲的是神经网络的基本原理。首先看这个公式……

[00:01:20] 李同学:
老师,这里为什么要用 sigmoid?
```

#### 视图 B:时间轴(精确核对)

```
[00:00:03 - 00:00:11]  张老师   今天我们要讲的是
[00:00:11 - 00:00:18]  张老师   神经网络的基本原理
[00:01:20 - 00:01:24]  李同学   老师,这里为什么
```

#### 视图 C:纯文本(喂给 LLM / 复制)

```
张老师:今天我们要讲的是神经网络的基本原理。首先看这个公式……
李同学:老师,这里为什么要用 sigmoid?
```

### 6.3 段落合并规则(对话体专用)

Whisper 会把一句话切成多段,直接显示会碎。**合并是纯展示层逻辑,底层 Segment 永远不动。**

```
相邻 segment 满足以下全部条件才合并:
  ① 同一 speaker_id
  ② 时间间隔 < 2.5 秒
  ③ 合并后时长 <= 60 秒
  ④ 合并后字数 <= 200 字
  ⑤ 不在句末标点(。!?…)之后断开
```

```rust
pub struct MergePolicy {
    pub max_gap_ms: u64,       // 2500
    pub max_duration_ms: u64,  // 60_000
    pub max_chars: usize,      // 200
}

pub fn merge_for_dialogue(segments: &[Segment], p: &MergePolicy) -> Vec<Utterance>;
```

**时间戳取该段落的起始时间**,这样点击时间戳能精确跳到这句话开始的地方。

### 6.4 改名不重写转写

```
❌ 错误:改名 → 重写 transcript JSON 里所有 display_name
✅ 正确:改名 → 只写 speaker_labels/<hash>.json,或只更新 transcript 的 speakers 段
```

配合 §5.3 的拆分设计,改名代价从 500KB 重传降到几百字节。

## 7. 说话人区分(Diarization)

### 7.1 ★ 线上会议不需要 diarization(最重要的优化)

**你的录制路线自带一个白送的红利。**

`tauri-plugin-system-audio` 的设计是:麦克风和系统声音输出为**两条独立轨道,不做混音**:

```
麦克风        → 重采样 16k → AEC3 → FrameEvent::Pcm(Mic)
系统 loopback → 重采样 16k → AEC3 → FrameEvent::Pcm(Loopback)
```

所以:

| 场景 | 说话人来源 | 准确率 |
|---|---|---|
| **线上会议/网课** | 轨道 1 = 对方,轨道 2 = 你 | **接近 100%** |
| **线下课堂** | 同一麦克风里,必须做 diarization | 15~30% 错误率 |

**"轨道分离" 是在直接知道谁在说话;diarization 是在猜。不要为了架构统一而放弃这个优势。**

AEC3 回声消除同样重要:没有它,对方的声音会从扬声器串进麦克风被识别两遍。

### 7.2 线下课堂:三档人数策略

```
音频 → ① VAD 切语音段
     → ② 每段提取声纹嵌入            ← 慢,缓存
     → ③ 聚类成 N 个说话人            ← ★ 难点
     → ④ 每段归属说话人 → 与转写段落对齐
```

**③ 为什么是关键:**

| | 自动检测人数 | **指定人数** |
|---|---|---|
| 算法本质 | **搜索**(不知 k,要多次评估或用阈值) | **求解**(k 已知,直接算) |
| 典型算法 | 层次聚类 + 阈值停止(阈值极难调) | k-means / 谱聚类,固定 k |
| 计算量 | 大 | **小** |
| 失败模式 | **过分割**(一个人被拆成多个) | 不会过分割,必定 N 个人 |
| 参数敏感度 | 阈值差一点结果差很多 | 基本不敏感 |

**结论:指定人数把开放集聚类降级成封闭集分类,难度不是一个量级。**

**三档策略:**

```rust
pub enum DiarizeMode {
    Auto,          // 省事,长音频容易过分割
    Fixed(u8),     // ★ 知道人数时最准,强烈推荐
    Range(u8, u8), // 折中
}
```

**UI 设计:**

```
发言人数量
  ( ) 自动检测
  (•) 指定人数   [ 4 ]
        建议:自动检测估计为 4 人,可以改
  [ 重新分离 ]     ← 秒级,不用重跑嵌入提取
```

### 7.3 人数给错的反向风险

| 用户输入 | 实际 | 后果 |
|---|---|---|
| 3 | 5 | **强行合并** → 两人被当成一人(总结会张冠李戴) |
| 5 | 3 | **强行拆分** → 一人被切成两人 |

自动检测出错通常是 "碎一点",可以手动合;**指定人数出错是系统性归错,更难发现。**

**所以不要让用户盲填 —— 永远先给一个自动估计值作为默认。**(见 §7.5 的交互设计)

### 7.4 段落级重叠投票(避开 CJK 字级时间戳的坑)

⚠️ **`whisper.cpp` 的 `--max-len 1`(字级时间戳)在 CJK 语言上工作得很差。**
而 "文本与说话人对齐" 的标准做法正是字级时间戳 —— **这条路对中文不通。**

**改用段落级重叠投票:**

```rust
/// 对每个转写段落,找重叠时长最长的说话人
pub fn assign_speaker(
    seg: &Segment,
    intervals: &[SpeakerInterval],
) -> (u32, bool) {   // (speaker_id, overlapped)
    let mut by_speaker: HashMap<u32, u64> = HashMap::new();
    for iv in intervals {
        let ov = overlap_ms(seg.start_ms, seg.end_ms, iv.start_ms, iv.end_ms);
        if ov > 0 { *by_speaker.entry(iv.speaker_id).or_default() += ov; }
    }
    let total: u64 = by_speaker.values().sum();
    if total == 0 { return (UNKNOWN_SPEAKER, false); }

    let mut ranked: Vec<_> = by_speaker.into_iter().collect();
    ranked.sort_by_key(|(_, v)| std::cmp::Reverse(*v));

    let (top_id, top_ov) = ranked[0];
    // 前两名比例接近 → 标记为重叠/不确定
    let overlapped = ranked.len() > 1
        && (ranked[1].1 as f32 / top_ov as f32) > 0.75;
    (top_id, overlapped)
}
```

**好处:** 不受时间戳粒度限制、天然能标记重叠语音、实现简单。
**代价:** 段落内真有两人交替时会归错一人 —— 对纪要和课堂笔记完全够用。

### 7.5 ★ 嵌入缓存 + 可反复重聚类

**把 ② 和 ③ 拆开,这是整个 diarization 设计中体验最好的一点:**

```
② 提取声纹嵌入     ← 慢(几分钟),只做一次,缓存到 speaker_embeddings 表
③ 用指定 k 聚类    ← 快(秒级),可以随便重跑
```

**效果:用户改人数 → 点 "重新分离" → 几秒钟出结果 → 看着不对再改。**

试错成本几乎为零。这比 "一次跑对" 更重要,因为 **diarization 本来就不存在 "一次跑对"**。

缓存键:`hash(audio_hash, segmentation_model, embedding_model, backend)`(见 §4.8)

### 7.6 模型与依赖

| 组件 | 选型 |
|---|---|
| 运行时 | sherpa-onnx(`sherpa-rs` crate),**纯 Rust,无 Python** |
| 分割模型 | `segmentation-3.0.onnx`(pyannote 系) |
| 声纹模型 | `3dspeaker_*.onnx` |
| **后端** | **CPU 兜底,GPU 可选加速**(见 §3.6) |

**不选 pyannote 的理由:** 精度略好,但要打包 Python 运行时分发。用 trait 包一层,将来真觉得精度不够再换,上层不动。

## 8. 声纹档案(跨会话辨认)

### 8.1 概念区分

| | 说话人**区分** | 说话人**辨认** |
|---|---|---|
| 问题 | 这段录音有**几个**人?哪句是谁? | **这个人**是不是张三? |
| 有无名字 | 只有 "说话人 1/2/3" | 直接是 "张三" |
| 跨录音 | ❌ 每次从零开始 | ✅ **有档案,可累积** |

**纯 diarization 是 "会话内" 的 —— 录 10 次课,它 10 次都从零开始猜。声纹档案补的就是这个。**

### 8.2 原理

声纹模型把语音压成 192~256 维向量;同一个人的向量方向接近,不同人相差较远。

```
similarity = cos(embedding_new, embedding_profile)
```

### 8.3 ★ 档案是一组向量,不是一个向量

**存单个向量会非常脆:**

- 换个麦克风 → 向量差异可能比 "不同人" 还大(**信道差异是头号敌人**)
- 感冒、刚睡醒、语速突变 → 向量都会漂

**正确做法:档案 = 多个样本的加权中心(centroid)。**

```
① 每个样本 embedding 先做 L2 归一化       ← 余弦相似度退化成点积,数值更稳
② 按 (语音时长 × 质量) 加权平均           ← 不是简单平均
③ 只用质量最高的 top-K 个样本              ← 防止一次糟糕录音毒化档案
④ 中心再归一化,存为 profile.centroid
```

**这就是 "多录几次更准" 的数学原理:** 样本越多样(不同麦克风、不同场景),中心点越稳定。

### 8.4 ★ 登记零额外操作

**不需要专门做 "录一段话登记声纹"。因为:**

> **"改发言人名字" 本身就是一次天然的声纹登记。**

用户把 "说话人 2" 改成 "张老师" 的那一刻,他刚刚确认了 "说话人 2 的所有语音 = 张老师"。**而手里已经有这个人整节课的声纹嵌入了** —— 这是极其优质的登记样本,远超 "对着麦克风读 10 秒"。

```
┌────────────────────────────────────────────────┐
│  发言人 2                                      │
│  名字  [ 张老师                    ]           │
│  时长  32:15 (68%)                             │
│  段落  147 条                                  │
│                                                │
│  保存声纹档案「张老师」?                        │
│  以后录音会自动识别并标注                       │
│                        [ 保存 ]  [ 暂不 ]      │
└────────────────────────────────────────────────┘
```

### 8.5 三级匹配:绝不静默猜错

```rust
if      sim >= 0.72 { MatchConfidence::Confirmed }  // 自动标注
else if sim >= 0.55 { MatchConfidence::Uncertain }  // "可能是 张老师?"
else                { MatchConfidence::New }        // 新建"说话人 N"
```

**为什么必须有中间档:**

- 猜对 → 用户没感觉
- **猜错 → 用户会把张三的话当成李四说的,而且完全不知道出错了** ← 错误不可见,这是灾难
- 标 "不确定" → 用户点两下确认,成本低但避免了不可见的错误

**这是准确率机制,不是合规机制。** 宁可多标几个 "待确认",也不要悄悄写错名字。

**而且 "确认" 和 "登记" 是同一个动作** —— 用户确认 "这确实是张老师" 时,顺手把这次嵌入加进档案。**用得越多越准。**

### 8.6 ⚠️ 档案污染(profile drift)

**绝对不要自动把每次匹配到的样本都加进档案:**

```
第1次:张老师 → 匹配成功(对) → 自动写入
第2次:张老师 → 匹配成功(对,但录音质量差) → 自动写入
第3次:李四的声音 → 误匹配成张老师 → 自动写入   ← 开始跑偏
第4次:档案已漂移,更易误匹配 → 恶性循环
```

**防护(全部要做):**

| 措施 | 说明 |
|---|---|
| **只登记用户确认过的样本** | 自动匹配到的一律不入库 |
| **保留原始样本,不覆盖** | 中心点是**算出来的**;档案坏了可重算、可回滚 |
| **限制单次样本权重** | 一次 3 小时的录音不该主导档案 |
| **质量门槛** | SNR 太低、时长太短(建议 < 3 秒)不入库 |
| **让用户能看见和清理** | "张老师 · 基于 7 次录音 · [查看样本] [删除某次]" |

**"保留原始样本 + 中心点可重算" 是让整个系统可逆的关键** —— 有了可逆性,调试和纠错的空间完全不同。

### 8.7 换个角度看:辨认让区分更准

一旦钉住了已知说话人,diarization 就从**开放集**变成**半监督**:

```
原来:不知道 k,无标签情况下猜有几类
现在:已确定 3 个人是谁(锚点),只需把剩余嵌入分给 2 个未知的人
```

**先跑辨认钉锚点,再对剩余部分做 diarization。** 1+1>2。

### 8.8 简化版设计(自用定位,无同意流程)

因为是自用工具,**不做**这些(前面讨论中确认删除):

- ❌ 采集他人声纹的同意勾选
- ❌ 隐私声明弹窗、反复提示
- ❌ 删除档案的二次确认
- ❌ 免责声明、合规章节

保留的防护(这些是功能不是甲):**三级匹配、质量门槛、原始样本、模型版本字段、一键纠正。**

**档案页 UI:**

```
声纹档案
  张老师    12 次 · 2.4 小时   [试听] [删除]
  李同学     8 次 · 0.7 小时   [试听] [删除]
  + 从文件新建
```

**首次引导里一句话:"声纹档案保存在本机,不会上传。"** 之后不再重复。

### 8.9 ⚠️ `embedding_model` 字段必须记

**换声纹模型 = 向量空间变了 → 所有旧档案和旧嵌入全部失效。**

没有这个字段,你会遇到 "换了模型后识别全乱但完全不知道为什么"。加载档案时校验模型名,不匹配就禁用该档案并提示。

### 8.10 准确率预期(诚实版)

| 场景 | 大致错误率 |
|---|---|
| 单次干净录音登记 | 3~5% |
| **多次登记 + 干净音频** | **1~3%** |
| **真实课堂**(远场、噪声、变麦克风位置) | **10~20%** |

**但不需要做到 100% 才有价值。** 因为用户可以改名字,正确的心态是:

> 价值不是 "完全自动化",而是**把用户从 "给每个发言人都从头标注" 降到 "扫一眼,改掉 3 个错"。**

147 个段落的转写,85% 准确率意味着只需改十几处,而不是从零标 147 处。**这是数量级提升,不是全有或全无。** 而且是**复利效应** —— 用得越久越准。

## 9. 自动场景判断与总结

### 9.1 两段式(不要一次做完)

一次调用干完(判断+总结)看似省事,但**判断错了整份纪要的结构就错了,而用户不知道怪谁。**

#### 第 1 段:场景判断(采样,不必全文)

```json
{
  "scene": "lecture",
  "confidence": 0.87,
  "evidence": "有'这节课''考试''作业'等课堂用语,单人长时间讲述",
  "suggested_focus": ["知识点", "例题", "作业布置"]
}
```

**输入必须采样开头 + 中段 + 末尾。** 只看开头有真实风险:很多会议开头是闲聊、很多课程开头是点名,**开头样本会误导判断**。

#### 第 2 段:按场景用不同模板

| 场景 | 总结结构 |
|---|---|
| **Lecture** | 知识点梳理 / 概念定义 / 例题与解法 / 作业与考试提示 / **复习提纲** |
| **Meeting** | 议题 / 决议 / **待办(负责人+截止)** / 分歧点 / 未决问题 |
| **Interview** | 主题脉络 / 核心观点 / 关键问答 / 金句 |

### 9.2 低置信度要 "说出来"

`confidence < 0.6` 时,UI 明确提示:

```
场景判断不太确定,已按【课堂】生成。  [切换为 会议]
```

**因为转写缓存在,切换模板重跑是秒级的。** 所以正确姿势是:**默认自动判断 + 一键切换兜底。**

### 9.3 长音频走 map-reduce

45 分钟课程 ≈ 9000~11000 字 ≈ 1.5 万 token。可以直接喂,但**效果会下降**(lost-in-the-middle —— 模型对长文中间部分注意力衰减)。

```
分段(按 5~10 分钟切,★ 必须在句子边界切)
  → 每段独立出"要点 + 关键结论 + 待办"
  → 聚合段做最终纪要(去重、合并、按主题重组)
```

**聚合阶段的 prompt 也必须按场景分支**,否则课堂会被聚合成干巴巴的要点堆砌,丢掉 "这是给学生复习用的" 这个本质。

**注意:这里的切块和 §3.4 的转写分块是同一套切分逻辑** —— 都必须在句子边界切,可以复用。

### 9.4 课堂特有的局限

**板书、公式、老师指着的 PPT 内容,ASR 完全抓不到。** 如果课程里 "这个公式" "看这张图" 很密集,纪要会出现大量悬空指代。

可选解法:允许手动附加截图/PDF 作为补充上下文。**这是加分项,不是必需项。**

### 9.5 输出 schema

```json
{
  "scene": "lecture",
  "summary": "本次课系统讲解了……",
  "sections": [
    { "title": "神经网络基本原理", "points": ["…"], "timestamps": [3120, 45000] }
  ],
  "key_concepts": [{ "term": "反向传播", "definition": "…", "timestamp": 123000 }],
  "homework": ["习题 3.1 - 3.5"],
  "review_outline": ["…"]
}
```

**会议场景追加:**

```json
{
  "decisions": ["…"],
  "action_items": [{ "task": "…", "owner": "张老师", "due": "下周三" }],
  "disagreements": ["…"],
  "open_questions": ["…"]
}
```

**注意 `timestamps`** —— 让纪要能点击跳回原话,这是录音转总结相比手写笔记的核心优势。

## 10. DeepSeek 集成

### 10.1 ★ base_url 必须可配置(即使现在只支持 DeepSeek)

**理由:**

- DeepSeek 是 **OpenAI 兼容协议**,客户端代码本来就该按 OpenAI 格式写
- 加了 `base_url`,**通义千问、Kimi、硅基流动、Ollama、私有部署**立刻可用,零代码改动
- 成本:一个输入框(约 10 行代码)。收益:整个供应商生态
- **反过来(先做死 DeepSeek 以后再抽)成本高得多**,因为 base_url 会散落各处

### 10.2 设置界面

```
供应商     [ DeepSeek ▾ ]        ← 内置预设,选它自动填好下面两项
API Key    [ •••••••••••••• ]    [测试连接]
Base URL   [ https://api.deepseek.com ]   ← 默认折叠,展开可改
模型       [ deepseek-chat ▾ ]   ← 预设列表 + 可手动输入
状态       ✅ 连接正常
```

### 10.3 模型下拉怎么做

- 内置**预设列表** + 允许**手动输入**
- **不要实时调 `/models` 接口填充下拉框** —— API 挂了或没网时界面会空
- 输入框旁给用途提示(用户不知道 `chat` 和 `reasoner` 该选哪个):
  - `deepseek-chat` —— 通用,总结首选
  - `deepseek-reasoner` —— 复杂推理,更慢更贵

### 10.4 密钥存储

**API Key 和 WebDAV 密码都走 Windows 凭据管理器(`keyring` crate),不进数据库、不进配置文件。**

理由不只是安全:配置文件会被同步、备份、截图。UI 上只显示掩码(`sk-****1234`),提供 "清除" 按钮。

### 10.5 错误映射(必须给可行动提示)

| 状态 | 用户看到的提示 |
|---|---|
| 401 | Key 无效或已过期,请到设置里重新填写 |
| 402 / 余额不足 | 账户余额不足,请充值 |
| 429 | 请求过于频繁,已自动重试(第 2/3 次) |
| 超时 | 网络不通,请检查代理设置 |
| 模型不存在 | 该模型不可用,请在下拉框中重新选择 |

最后一条尤其重要:模型名会变(旧模型下线),用户手填了失效名字时必须能看懂原因。

### 10.6 ★ prompt 结构(利用 DeepSeek 的缓存折扣)

DeepSeek 有**上下文缓存命中折扣**,命中缓存的输入 token 便宜很多。所以:

```
[放最前面、保持稳定]   系统提示 + 总结模板 + 术语表
[放后面、每次都变]     转写正文
```

**把稳定内容前置,让前缀缓存能命中。** 零成本优化,只是 prompt 拼装顺序问题 —— 但一开始把正文写在前面,后面改起来要动所有 prompt。

### 10.7 费用显示

设置页显示**每次调用的 token 用量和估算费用**(输入 / 输出 / 缓存命中分开显示)。

你选本地转写就是为了省钱,应该让用户看得见省了多少。价格不要写死,做成可配置或标注 "参考价"。

### 10.8 ★ 中文术语校正(建议列为必做)

**Whisper 在中文上会稳定犯这些错:**

| 类型 | 例子 |
|---|---|
| 同音混淆 | 知觉/直觉、实效/时效、权利/权力 |
| 专业术语 | 注意力机制 → 注意立即制、Transformer → 传斯佛默 |
| 人名机构名 | 几乎必错 |

`initial_prompt` 热词注入**能起作用但很弱**(Whisper 是 30 秒滑窗,提示只对窗口开头有效)。

**真正有效的做法是转写后加一步 "术语校正" LLM 调用:**

```
输入:整篇转写文字 + 用户术语表
约束:只修错别字和术语,不改写句子、不动时间戳
```

成本极低(几厘钱),但对最终纪要质量提升非常明显。

### 10.9 隐私边界(说一次就够)

UI 上说明一次:**音频永远不出本机,只有转写后的文字会发送给所选服务商。**

这不是免责,是让用户理解自己的数据边界 —— 也是 "本地转写 + 云端总结" 这个架构最大的卖点。

## 11. WebDAV 云端同步

### 11.1 目标环境:Seafile 系 WebDAV(已验证)

**目标网盘基于 [Seafile](https://cloud.example.com/doc/) 定制**,官方支持 WebDAV,并在手册中列出 [Zotero、Obsidian、rclone](https://cloud.example.com/doc/zotero/) 等集成方式。

**已实测的配置**(来源:本机 Zotero `prefs.js`):

```
URL       https://cloud.example.com/seafdav
用户名     <账号>@auth.local          例:2025000000@auth.local
协议      webdav
verified  true                        ← 已在生产使用中
```

**这个配置同时证明了:**

1. ✅ 认证方式(账号 + `@auth.local`,**不是 SSO 密码**)
2. ✅ 路径格式(`/seafdav` 端点)
3. ✅ WebDAV 在该账号可用
4. ✅ **能传大文件**(Zotero 同步几十 MB 的 PDF 附件)
5. ✅ **`MOVE` 原子改名可用**(Zotero 上传附件走的就是 "临时名 → MOVE")

> ⚠️ **WebDAV 密码不在 Zotero 的 prefs.js 里**(存在 Zotero 的登录管理器)。程序里单独存一份到 Windows 凭据管理器,不依赖 Zotero。

### 11.2 ★ Seafile WebDAV 的真正性能特点

Seafile 官方手册的警告:

> **Uploading large number of files at once is usually much slower than the syncing client. That's because each file needs to be committed separately.**
> So WebDAV is more suitable for **infrequent file access**.

**注意它说的是 "大量小文件",不是 "大文件"。** 这个区别是设计依据:

| 数据类型 | 文件数 | 单文件 | WebDAV 表现 |
|---|---|---|---|
| **音频文件** | 少 | 大(10~40MB) | ✅ 没问题,每个文件一次 commit,大文件反而摊销得好 |
| **转写/纪要** | **多** | 小(几十 KB) | ⚠️ 会慢 —— 每个文件单独 commit |

**所以正确的设计不是 "避免 WebDAV 传大文件",而是 "避免一次性推几百个小文件"。**

**同网段红利:** 客户端与网盘在同一内网时速度通常很高,音频同步基本不构成瓶颈。**因此 Opus 转码优先级可以降低** —— 先传原始文件,真觉得慢再开压缩。

(若日后要开压缩:单声道 16kHz Opus 32~48kbps 可把 45 分钟音频从 ~42MB 降到 ~10MB。但**有损压缩对中文远场录音的识别影响未经验证**,建议先做一次 A/B 再决定。)

### 11.3 ★ 混合传输方案(已确认)

```
走 WebDAV(程序可控、文件少、需要状态可见):
    manifest.json
    transcript/*.json
    summary/*.md
    profiles.json
    speaker_labels/*.json

交给 Seafile 客户端(文件大、传完不动、官方推荐方式):
    audio/**
```

**这个划分是有原则的:**

- **manifest 必须走 WebDAV** —— 它是同步状态本身,程序必须能直接读远端最新版本来合并。放进同步目录的话,"本地文件" 和 "远端状态" 会混在一起
- **文本按需传** —— 你是 "处理完一节课传一次",不是 "一次性同步 500 个文件",不会撞上 commit 性能问题
- **音频交给客户端** —— 大文件本来就该用它,而且省掉自己写断点续传(最易出 bug 的部分)

### 11.4 WebDAV 客户端实现

**决定:`reqwest` + 自己写薄封装,不套用现成 WebDAV crate。**

理由:需要的高级用法(ETag 条件请求、`MOVE` 原子改名、失败重试)通用库通常只覆盖基础 PUT/GET/PROPFIND,遇到就得绕开它 —— 那时候等于写了两遍。

**工作量估算:**

| 部分 | 行数 |
|---|---|
| `PROPFIND` 解析(`quick-xml`) | ~80 |
| 上传 + 校验 | ~100 |
| 下载 + 校验 | ~60 |
| 重试 / 退避 | ~40 |
| **合计** | **~300 行** |

**必做的三件事:**

```rust
// ① 原子写:传到临时名,完成后 MOVE
PUT  /recording-summary/audio/ab/ab3f9c...part
MOVE /recording-summary/audio/ab/ab3f9c...part  →  .../ab3f9c...

// ② ETag 条件请求:一致就跳过(增量同步基础)
PROPFIND → 取 ETag → 与本地记录比对 → 相同则 skip

// ③ 能力探测:启动时试一次,不支持就降级
//    不是所有 WebDAV 服务器都支持 Content-Range / MOVE
```

### 11.5 云端目录布局

```
cloud.example.com/seafdav/
    <Zotero 资料库>/              ← Zotero 在用,不要动
    recording-summary/            ← 本项目,新建
        manifest.json
        profiles.json
        transcript/ab/ab3f9c...e21.json
        speaker_labels/ab/ab3f9c...e21.json
        summary/ab/ab3f9c...e21.md
```

**用内容哈希做路径的三个好处:**

- **路径就是内容哈希** → 两台设备录到同一节课只存一份(**去重白送**)
- **不需要列目录** → 想知道文件在不在,直接 `PROPFIND` 那一个路径(PROPFIND 递归列目录很慢)
- **文件名不含中文/空格** → 避开 WebDAV 的 URL 编码兼容性问题

前两位哈希做子目录,避免单目录文件过多。

### 11.6 ★ manifest.json 设计

```json
{
  "version": 1,
  "files": {
    "ab3f9c...e21": {
      "audio":      { "size": 10485760, "etag": "\"a1b2c3\"",
                      "synced_at": 1730000000000, "origin": "desktop" },
      "transcript": { "etag": "\"d4e5f6\"", "synced_at": 1730000000000 },
      "summary":    { "etag": null },
      "labels":     { "etag": "\"9a8b7c\"", "synced_at": 1730000000000 }
    }
  },
  "profiles": {
    "p_7f3a": { "display_name": "张老师", "updated_at": 1730000000000 }
  }
}
```

**为什么是单个文件而不是每设备一份:**

| 好处 | 说明 |
|---|---|
| **一次 `PROPFIND` 知道全部状态** | 不用遍历远程目录,秒级判断 "哪些没传" |
| **可读可改可备份** | 出问题直接打开看,甚至手动改 |
| **增量同步简单** | 比对本地记录和 manifest,差集就是要传的 |
| **体积小** | 500 节课约 30KB |

**冲突处理:manifest 是 "事实的追加日志",不是 "状态的快照"。**

```
① 每条记录只追加不删(文件存在这个事实不会变)
② 两边都有 → 按 synced_at 取新的合并
③ 上传前先 GET 最新的 manifest,合并后再 PUT   ← 这就是锁,单人场景够用
```

**★ 关键:manifest 可重建。** 就算整个丢了或损坏,程序扫一遍本地数据 + `PROPFIND` 远程目录就能重新生成。**所以它不需要任何事务保护,坏了就重建。** 这让实现简单一大截。

### 11.7 冲突处理:一个字段就够

```sql
last_modified_at INTEGER,   -- 毫秒时间戳
origin_device    TEXT       -- 哪台机器改的,用于排查
```

| 数据类型 | 合并规则 | 为什么 |
|---|---|---|
| **转写、纪要**(生成后不变) | **只增不改**,存在就跳过 | 不可变数据没有冲突 |
| **名字映射、session 标题** | **时间戳新的赢** | 可变,但不可能同时在两台机器改同一个 |
| **声纹登记样本** | **只追加**,按 sample_id 去重 | 天然可合并 |

**核心原则:让尽可能多的数据变成 "不可变" 的。** 改名是改标签层(`speaker_labels/*.json` + `profiles.json`),不动转写本身 —— **这正是 §4.8 缓存键不含名字、§5.3 标签拆分的红利。**

### 11.8 ⚠️ 时钟偏移校验

时间戳取胜的前提是两台机器时钟一致。同步时校验服务器 `Date` 头与本地时间,偏移超过几分钟就提示。

**5 行代码,能避免 "改了名字却同步不回来" 这类查不出的怪问题。**

### 11.9 状态只存一处

**同步状态只存 manifest。** 不要一部分在本地 SQLite、一部分靠遍历远端推断 —— 那样一旦不一致你就完全没法排查。

### 11.10 安全底线

- **必须 HTTPS**(HTTP 下密码和录音明文过网)
- **用应用专用密码**,不复用主密码
- WebDAV 凭据走 Windows 凭据管理器

### 11.11 ⚠️ 账号有期限 —— 硬性提醒

该网盘的用户手册明确:

> 在校师生是长期账号,**离校后将回收**
> 校友无法登录 → **180 天锁定期** → **365 天后自动清理归档账号并释放全部资源**

**结论:云盘只能作为 "多设备中转站",绝不能作为 "唯一备份"。**

- 本地必须保留完整副本(架构本来就是本地优先)
- 重要录音建议**双轨备份**(同时留一份在移动硬盘)

### 11.12 工作量

| 阶段 | 内容 | 估时 |
|---|---|---|
| ~~S3 音频转码 + 续传~~ | **删掉**,交给 Seafile 客户端 | — |

## 12. 坑点清单

按踩到有多痛排序。

### 12.1 ⚠️ whisper.cpp 各后端都要自行编译

**官方默认 Release 只带 CPU/Metal 后端。**

| 后端 | 获取方式 | 难度 |
|---|---|---|
| CPU | 官方 Release 自带 | ✅ 无 |
| **CUDA** | 需 CUDA Toolkit + CMake 自行编译 | ⚠️ **中等,唯一可能卡住的** |
| **Vulkan** | 需 Vulkan SDK + CMake 自行编译 | ⚠️ 中等 |
| Metal | 官方 Release 自带(macOS) | ✅ 无 |

**这是整个项目唯一可能卡住的外部依赖,建议放在第 1 天做。**

**★ 但不要一次编译全部后端。** 建议顺序:

```
第 1 天:只编 CUDA 版(开发机自用,最快)
W4 之后:再编 Vulkan 版(多机器兼容)
```

**先用 CUDA 验证整条链路能跑通,再考虑多后端。** 否则你会在环境配置上花掉一周却没写一行业务代码。

预期性能(RTX 4060 Laptop 8GB + `large-v3-turbo` int8,约 1.6GB 显存):**15~25× 实时**,45 分钟音频约 2~3 分钟。

### 12.2 ⚠️ 双轨录音的时钟漂移与静音回调

同时录 "系统声音 + 麦克风" 时:

| 问题 | 解决 |
|---|---|
| **时钟漂移** | 两个独立时钟设备,长时间会漂移。★ **采集时给每帧打单调时钟时间戳**,按共享时间轴归并 |
| **静音不回调** | WASAPI loopback 在系统完全静音时不产生数据回调,直接拼流会时间轴错位。**必须补静音帧** |
| **采样率不一致** | loopback 通常 48kHz 立体声,麦克风可能 44.1kHz。统一重采样到 16kHz 单声道 |

**★ 时间戳必须在写采集代码的第一天就做进去,事后补非常痛苦。**

`tauri-plugin-system-audio` 已帮你处理了重采样到 16k 单声道和 AEC3 回声消除,但**跨轨归并仍需自己处理**。

### 12.3 ⚠️ CJK 没有可靠的字级时间戳

`whisper.cpp` 的 `--max-len 1`(字级时间戳)**在 CJK 上工作得很差**。而文本与说话人对齐的标准做法正是字级时间戳 —— **这条路对中文不通**。

**解法:段落级重叠投票**(见 §7.4)。

### 12.4 模型文件与权限

- 模型**别放程序目录** —— Windows 下 `Program Files` 无写权限。放 `%APPDATA%\<AppName>\models\`
- 首次启动要有**模型下载管理器**:选模型、进度、SHA256 校验、断点续传
- **提供备用镜像 URL** —— HuggingFace 在国内可能很慢,否则用户第一次打开就卡死
- **★ 模型档位要跟着硬件走**(见 §3.3),不要让 CPU-only 的机器默认下 1.6GB 的大模型

### 12.5 ffmpeg 随包分发

用户不会自己装。用 `ffmpeg-static` 或随包分发二进制。

(本机当前**未安装 ffmpeg**,需要处理。)

### 12.6 长任务不能阻塞 UI

- 跑在 `tokio::task` / 独立线程
- 通过 Tauri 事件推进度(`pipeline://progress`)
- **★ 支持取消** —— 用户点错文件要能中止,而不是干等
- **★ CPU 模式下尤其重要**:一小时的任务必须能取消,且已完成部分要保住(§3.4)

### 12.7 分阶段显示结果(体验关键)

diarization 会让处理时间翻倍。**不要等全部跑完才显示:**

```
阶段 1:转写完成 → 立刻显示全文(可读、可搜索)   ← 用户马上有东西看
阶段 2:diarization 完成 → 时间轴刷新出说话人标签  ← 后台继续跑
```

45 分钟音频多等 3 分钟,体感很差。

### 12.8 声音档案相关的三个坑

见 §8.6(污染)、§8.9(模型版本)、§8.5(静默猜错)。

### 12.9 多后端相关的坑

| 坑 | 对策 |
|---|---|
| 探测到 GPU 但实际转写失败 | **必须做微型转写自检**,不能只看 `nvidia-smi`(§3.2) |
| 用户以为用了 GPU 其实在用 CPU | UI 上**显式显示实际后端**,不要静默降级(§3.3) |
| 同一模型跨后端结果有细微差异 | `backend` 进缓存键(§4.8) |
| 装了大模型但机器跑不动 | 模型档位跟着硬件自动选(§3.3) |
| 安装包因多后端而巨大 | 默认只带 CPU + Vulkan,CUDA 按需下载(§3.5) |

### 12.10 WebDAV 相关的坑

见 §11.2(批量小文件)、§11.8(时钟偏移)、§11.11(账号期限)。

|---|---|
| 交付 | manifest 合并、增量同步、同步状态 UI |
| **验收** | 设备 A 处理完 → 设备 B 能读到转写和纪要,发言人名字正确显示 |

### 依赖关系

```
W1 ──→ W2 ──→ W3
        │      │
        └──────┴──→ W4 ──→ W5 ──→ W6
```

**关于 W5 的位置说明:** 多后端本质上是 `Transcriber` 的一个实现细节,不影响业务逻辑。**把它排在 W4 之后是有意的** —— 先在开发机上用 CUDA 把整条链路跑通(那是你最需要的功能),再扩展现有代码去适配别的硬件。反过来做的话,你会在环境配置上消耗掉最初的开发热情。

**但架构上必须从第一天就留位置:** `AsrOpts` 带 `backend` 字段、`Transcript` 记录 `backend`、缓存键含 `backend`。这些在 W1/W2 就要写对,后期补会牵连缓存和已有数据。

### W2 之后的能力边界

即使 GUI 和同步都没做,**W2 结束时你已经有一个真正能干活的东西**:丢进一个 mp3,出来带说话人、带场景适配结构的纪要,而且改模板重跑是秒级的。

## 14. 录音条件与设备选择

> 本章回答:**音频从哪来、要录成什么样、值不值得买设备。**
> 这是实际使用时最常要查的操作性知识,也是决定 "什么时候能用上" 的关键 —— 手机/录音笔导入是零开发成本的路径(见 §14.7)。

### 14.1 ★ 核心前提:总结比转写耐错得多

**这一条决定了整套流程对录音条件的要求比 "做转写" 低一大截。**

| 用途 | 需要的准确率 | 70% 准确率的后果 |
|---|---|---|
| **逐字稿 / 引用原话 / 法律记录** | 95%+ | 完全不可用 |
| **结构化总结** | **70~80% 就够** | 摘要依然能抓住 90% 的内容 |

**为什么总结这么耐错 —— 三重缓冲:**

- **冗余** —— 老师讲一个概念会换着说法讲好几遍,错一遍不影响抓重点
- **上下文补偿** —— "注意立即制" 这种错词,LLM 看到上下文能推出是 "注意力机制"
- **只关心要点** —— 漏掉的那句大概率是重复解释

**而且错误有兜底:术语校正环节(§10.8)专门处理同音字和术语错认。**

**结论:录音条件差不是 "能不能用" 的问题,而是 "错别字多一点" 的问题。**

### 14.2 质量影响因素的优先级

按影响程度排序 —— **注意设备本身排得很靠后:**

| 排名 | 因素 | 影响 | 能否花钱改善 |
|---|---|---|---|
| **1** | **距离 + 混响** | ★★★★★ | ✅ 能,这是唯一真正有效的花法 |
| **2** | **麦克风指向性** | ★★★ | ✅ 能(心形/超心形) |
| **3** | 多人语音重叠 | ★★★ | ❌ 不能,只能靠录音布置规避 |
| **4** | 背景噪声 | ★★ | ❌ 影响相对小 |
| **5** | 麦克风绝对素质 | ★★ | ⚠️ 边际收益递减很快 |
| **6** | 采样率 / 位深 | ☆ | ❌ **基本无关**,Whisper 反正会重采样到 16kHz |

#### ① 距离和混响 —— 头号杀手

| 设备位置 | 大致效果 |
|---|---|
| **讲台 / 第一排桌上** | ✅ 很好,接近理想 |
| 中间排桌上 | ⚠️ 可用,混响开始明显 |
| **后排 / 放包里** | ❌ 混响 + 距离双重打击,错误率可能翻几倍 |

教室和阶梯教室的**混响**比想象的严重 —— 硬墙、大空间、声波来回反射,Whisper 对混响相当敏感。有专门的模型路线([Whisper-RIR-Mega](https://huggingface.co/mandipgoswami/whisper-medium-rirmega))就是为混响语音微调的,说明这是公认难点。

#### ② 多人重叠

- 老师单向讲述 → 最好
- 课堂互动、小组讨论 → 明显变差
- 会议多人抢话 → 最差

**多人重叠时 ASR 和说话人区分会同时劣化**,没有任何设备能解决。

#### ③ ⚠️ 反直觉:设备 "降噪" 可能帮倒忙

**这条必须记住,而且录音设备上这个开关默认往往是开的。**

有研究直接叫[《When Denoising Hinders: Revisiting Zero-Shot ASR》](https://ar5iv.labs.arxiv.org/html/2603.04710) —— **语音增强反而损害 Whisper 的识别。**

原因:

- Whisper 是在**真实含噪语音**上训练的,它自己会处理噪声
- 而设备的降噪算法是为**人耳好听**优化的,会削掉一些人耳不敏感、但模型需要的声学细节

**结论:录音时关闭所有 "人声增强 / AI 降噪 / 会议模式",用最朴素的原始录音。** 成本为零,但很多人会开反。

### 14.3 手机 / 录音笔 / 领夹麦 横向对比

| 维度 | 手机 | 录音笔 | 无线领夹麦 |
|---|---|---|---|
| **能放的位置** | 你人在哪它在哪 | ✅ **可放讲台,你坐后排** | ✅ 别在说话人身上 |
| **指向性** | 通常全指向(波束成形仅通话时生效) | ✅ 心形/超心形,压混响 | ✅ 近场,绕开混响 |
| **连续录制** | 来电话会中断 | ✅ 十几小时 | ✅ 数小时 |
| **电池** | 一天两充,连录 3 节要挂充电宝 | ✅ 20~40 小时 | ✅ 发射器数小时 |
| **存储** | 可能录满 | ✅ 8~32GB | 取决于接收端 |
| **操作可靠性** | 容易误触停止 | ✅ 物理推钮 | ✅ 一键 |
| **麦克风素质** | 现代手机其实不错 | 通常更好(中高端) | ✅ 最好(离嘴 15cm) |
| **便携** | ✅ 本来就要带 | ❌ 多带一件 | ⚠️ 两个部件 |
| **社交成本** | 无 | 无 | ❌ **要请对方佩戴** |
| **花费** | 0 | 300~800 元(中端) | 100~300 元 |

#### 关键推论

```
★ 一支 200 元的录音笔放在讲台上,效果明显好于一台旗舰手机放在第五排。
★ 反过来,手机放在讲台上,和录音笔放讲台上,差距会小很多。
```

**录音笔的价值不在于 "音质更好",而在于「能放在更好的位置 + 心形指向压制混响」。**

参考:评测普遍认为[手机直连麦克风已能替代 90% 专业录音设备](https://post.smzdm.com/p/agg09l0d/)。

#### ⚠️ 别买低价档

100~200 元的 "录音笔",麦克风素质**未必比手机好** —— 便宜产品经常只是 "更差的麦克风 + 更大存储"。**这个价位不如把钱花在手机配件上。**

### 14.4 按场景的设备选择

| 场景 | 推荐 | 理由 |
|---|---|---|
| **线上会议 / 网课** | ✅ **系统声音录制**(§7.1) | 数字音频无损 + 说话人天然分离。设备再好也比不过直接抓音频 |
| **线下课堂** | 手机放前三排 → 不够再上录音笔 | 详见 §14.6 决策树 |
| **现场会议** | 手机平放桌面中间 | "手机放桌上开会" 是标准做法,效果通常尚可 |
| **能跟讲者商量** | ★ **无线领夹麦** | 技术最优解:SNR 高一个量级,绕开混响,且天然单人 |

**领夹麦是技术上最优解,但它的障碍不是技术而是社交成本。** 如果能商量,这是性价比最高的方案 —— 效果最好,还最便宜。

### 14.5 设备选购要点

#### 真要买录音笔,只看这 4 个参数

```
① 指向性 —— 优先"心形/超心形",不要全指向     ← 最重要,压教室混响
② 录音格式 —— 支持 WAV 或高码率,能关闭降噪   ← 见 §14.2 ③
③ 续航 —— ≥ 15 小时                        ← 撑得住一整天的课
④ 存储 —— ≥ 8GB 或支持扩展卡                 ← 无损录音很占空间
```

**其余参数不用看:**
- 采样率 44.1k 还是 48k → **对 Whisper 无区别**
- 位深 16 还是 24 → **无区别**
- 32bit 浮点、超低底噪、专业接口 → **为音乐和采访设计,对 ASR 收益极小**
- **高端录音笔(1000+ 元)在你的场景不划算**

#### 买回来第一件事

**试录一段,确认所有降噪/AI 增强已关闭**,使用 "原始/无处理" 模式。

这一步不做,可能花了几百块却得到比手机更差的结果(原因见 §14.2 ③)。

### 14.6 录音操作清单与决策树

#### 录音前

```
[ ] 座位:尽量前三排,或把设备放在讲台附近
[ ] 位置:平放桌面,麦克风朝向讲者
         ❌ 不要放包里 / 拿在手里(摩擦声)/ 放口袋
[ ] 设置:★ 关闭人声增强、AI 降噪、会议模式
[ ] 格式:WAV,或高码率 AAC/m4a;避免"语音备忘录"的压缩模式
[ ] 模式:飞行模式或勿扰,避免来电中断
[ ] 电量:确认够用;边充边录可能有电流噪声
[ ] ★ 试录:上课前录 1~2 分钟回放确认      ← 最省事的一步,别省
```

**"试录" 这条千万别省。** 录完两小时课才发现设备在包里、全程闷响 —— 这事提前一分钟就能发现。

#### 你该不该买录音笔

```
买,如果:
  ✅ 一周录 5 节以上,想"扔在讲台就不用管"
  ✅ 经常录 2 小时以上的长课,不想担心电量和中断
  ✅ 不想占用手机(录着课还要拍 PPT)
  ✅ 座位常在中间或后面,手机够不到讲台

不买,如果:
  ❌ 本来就坐前三排(手机够好了)
  ❌ 一周只录一两节(手机 + 飞行模式完全够)
  ❌ 预算低于 300(买不到比手机更好的麦克风)
  ❌ 线上会议为主(那是系统声音录制的活)
```

#### 推荐的推进顺序(避免白花钱)

```
第 1 步:用手机录两节课(前三排、平放桌面、飞行模式、关降噪)
         → 导入程序跑一遍,看转写和总结质量
         ★ 这一步免费,且大概能解决 80% 的问题

第 2 步:质量够用 → 省下这笔钱
         质量不够 → 先确认瓶颈是"位置"还是"设备"
                    (把手机往前挪两排再试一次)

第 3 步:确认是设备问题,再考虑:
         能跟老师商量 → 无线领夹麦(效果最好,还最便宜)
         不能商量     → 中端录音笔(300~800 元),放讲台
```

**说句实在话:现在的瓶颈不在硬件,在于整套流程还没跑起来。** 手机录音的质量足够得到一份可用的课程纪要,而 "能不能拿到这份纪要" 取决于 W1/W2 的开发进度,不取决于录音设备。

### 14.7 预期效果与开发顺序

#### 效果预期(诚实版)

| 录音条件 | 转写效果 | 总结可用性 |
|---|---|---|
| 讲台 / 第一排 | 很好,少量同音错字 | ✅ **完全可用** |
| 中间排 | 可用,错字明显增多 | ✅ **可用**(术语校正后) |
| 后排 / 放包里 | 错误较多 | ⚠️ 大意能抓到,细节会丢 |
| 多人讨论重叠 | 差 | ⚠️ 能看出讨论了什么,但归属会乱 |

**一句话:前三排的录音 → 一份错字略多但要点齐全的笔记。**

#### 对开发顺序的影响

| 路径 | 需要开发 | 什么时候能用 |
|---|---|---|
| **手机 / 录音笔录音 → 导入文件** | **零**(走已有的 `FileSource`) | **W2**,约 2 周 |
| 系统声音录制 | 有 | W3 |

**两个重要推论:**

1. **手机录音导入是零开发成本的路径** —— 导入文件本来就在架构里(§2.2 的 `FileSource`),手机只是个文件来源。**W2 之后就能用真实课程跑起来。**
2. **买不买录音笔对开发没有任何影响** —— 录音笔的文件走的是和手机完全相同的 `FileSource` 路径。所以可以随时买、随时用,不用等程序改。

**因此建议:W2 之后先用手机录一段时间真实课程。** 你会立刻知道这套流程值不值,而且这段时间正好用来验证转写质量和总结模板 —— 等 W3 上录音功能时,你已经知道该往哪个方向调。

### 14.8 与说话人区分的关系

| 录制方式 | 说话人区分 |
|---|---|
| **系统声音 + 麦克风双轨** | ✅ **天然分离,接近 100%**(§7.1) |
| 手机 / 录音笔单文件 | ❌ **只有单轨,只能靠统计推断**,课堂场景 15~30% 错误率(§8.10) |

**单文件录音下,说话人区分几乎必然不准。** 但功能都在 —— 时间戳、发言人、可改名 —— 只是 "发言人 1/2/3" 的归属需要多改几处。

**这正是三级匹配(§8.5)和手动改名存在的意义。** 而且配合声纹档案,同一批人第二次录音时准确率会明显提升。

## 附录 A:一句话总结每项决策

| 决策 | 一句话理由 |
|---|---|
| 本地转写 + 云端总结 | 音频不出机器;只有文字上云,成本可忽略 |
| src-core 独立于 GUI | 转写要跑几分钟,GUI 里 debug 是折磨 |
| sidecar 而非 FFI | 子进程崩溃不影响主程序;**换后端只是换 exe 路径** |
| 多后端 + 运行时自动降级 | Vulkan 一个二进制覆盖 AMD/Intel/NVIDIA;CPU 永远兜底 |
| **必须做微型转写自检** | `nvidia-smi` 说有 GPU 不等于真能跑;驱动/库/显存都可能失败 |
| **手动指定后端时不静默降级** | 否则用户会困惑 "为什么这么慢" |
| **模型档位跟着硬件走** | CPU-only 上跑大模型是 1.5~4 小时,必须自动选小模型 |
| **分块转写 + 断点续传** | CPU 模式下这是从 "不可用" 到 "可用" 的差别 |
| **backend 进缓存键** | 跨后端结果有细微差异,不进键会拿到对不上的缓存 |
| 缓存键含 diarization 配置但不含名字 | 改配置要重算;改名字是展示层,不该重算 |
| 双轨独立而非混音 | 线上会议的说话人是 "直接知道" 而不是 "猜" |
| 指定人数 + 嵌入缓存 | 把开放集聚类降级为封闭集求解,且试错成本为零 |
| 声纹档案 = 加权中心 | 单个向量对信道差异太脆 |
| 改名即登记 | 零额外操作;这是 "越用越准" 的入口 |
| 三级匹配 | 猜错且不可见是灾难;中间档让错误可见 |
| 保留原始样本 | 中心点必须可重算,否则算法一改旧数据就废 |
| 存储结构化 / 显示派生 | 时间戳跳转、搜索、重新对齐都需要结构化字段 |
| 标签文件独立拆分 | 改名从重传 500KB 降到几百字节 |
| 文件是真相源,数据库是缓存 | 数据库可重建 → 不需要处理数据库合并冲突 |
| manifest 单文件 | 一次 PROPFIND 知道全部状态,且可重建所以不用事务保护 |
| 内容哈希做路径 | 去重白送 + 不需要列目录 |
| 文本走 WebDAV,音频交客户端 | Seafile 的弱点是批量小文件,不是大文件 |
| 云盘只做中转站 | 机构账号可能被回收,不能当唯一副本 |
| 总结比转写耐错 | 70~80% 准确率仍能抓住 90% 的内容,所以录音条件要求不高 |
| **关闭设备降噪** | ★ 反直觉:语音增强反而损害 Whisper,它是在含噪语音上训练的 |
| 手机录音导入优先 | 零开发成本,走已有的 `FileSource`;W2 就能跑真实课程 |
| 录音笔不是首要投资 | 决定音质的是距离和混响,不是设备;先试免费的前排座位 |

## 附录 B:文档维护注意事项

**⚠️ 编辑本文档时不要用 PowerShell 的 `Get-Content` / `Set-Content`。**

本机 `pwsh` 实际是 **Windows PowerShell 5.1**,其 `Get-Content` 默认按系统 ANSI 代码页(GBK)解析文件。用它读取 UTF-8 中文文档再写回,会**永久损坏编码**(部分字节经 GBK 解码后会变成 `?`,不可逆)。

**正确做法:** 用支持 UTF-8 的编辑器,或用文件读写工具直接操作字节。

**如果必须用脚本处理,显式指定编码:**

```powershell
$txt = [System.IO.File]::ReadAllText($path, [System.Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($path, $new, (New-Object System.Text.UTF8Encoding($false)))
```

## 16. 实现现状与验证结果

> **本章是 v1.3 新增的"事后回填"。** 前面各章是设计意图,这一章记录**实际做出来之后**
> 发现与设计不符的地方、以及哪些结论得到了实测支持。
> 保留差异本身有价值 —— 它记录了哪些判断是推测、哪些是验证过的。

### 16.1 与设计不符的三处

#### ① 说话人区分的缓存对象变了

**原设计(§4.8 / §7.5):** 缓存**声纹嵌入**,让"改人数"秒级重跑。

**实际实现:** sherpa-onnx 把「分割 → 嵌入提取 → 聚类」封装成一个整体调用
(`SherpaOnnxOfflineSpeakerDiarizationProcessWithCallback`),**中间嵌入拿不到**。

**改成的方案:** 缓存**说话人时间区间**(`diarize_cache` 表)。效果相近 ——
改人数时仍能跳过最贵的那一步。但代价要说清楚:

| | 原设计 | 实际实现 |
|---|---|---|
| 改人数重跑 | 只重跑聚类(秒级) | 仍需进入 sherpa 内部重新聚类 |
| 缓存内容 | 每段嵌入向量 | 说话人区间 |
| 实现复杂度 | 高(要自己写聚类与缓存) | 低(直接用 sherpa 的结果) |

**缓存键刻意不含 `DiarizeMode`** —— 用户会反复改人数试效果,模式进键就等于每次都是一个新条目,缓存形同虚设。

#### ② 声纹档案的嵌入来源不存在

**原设计(§8.3):** 用会话内的声纹嵌入算加权中心。

**实际:** 同样因为嵌入拿不到。**当前库层完整实现(加权中心、三级匹配、防污染、可重算),
但缺少"从会话提取嵌入"这一环。** 如实标注为待补。

替代路径是 sherpa 的 `SpeakerEmbeddingExtractor`(独立的说话人识别接口),
接上它就能补齐 —— 见 §16.4。

#### ③ WebDAV 同步的实现顺序

**原设计(§11.3):** 混合传输(文本走 WebDAV、音频交 Seafile 客户端)。

**实际:** 这个划分**得到了 Seafile 官方文档的支持,但没有得到实测验证** ——
我没有用户的云盘账号。代码完整(含 ETag 条件请求、`MOVE` 原子写、manifest 合并、
能力探测),XML 解析有单元测试覆盖,但**真实服务器上的行为待验收**。

### 16.2 实测数据(设计阶段是推测,这里是量出来的)

#### 中文繁体偏好 —— 设计时完全没预料到

Whisper 在中文音频上**稳定输出繁体**。同一段音频、同一个模型:

| 配置 | 输出 |
|---|---|
| 无提示 | 同學們,這節課我們講神經網絡的基本原理 |
| `initial_prompt` 加「请使用简体中文」 | 同学们,这节课我们讲神经网络的基本原理 |

**而且顺带降低了同音字错误率**(实测「公示」→「公式」)。
已内建:`--language zh` 时自动附加提示,见 `src-core/src/asr.rs`。

#### 跨后端结果确实不同 —— 验证了缓存键设计的必要性

同一音频、同一模型(`tiny`),只换后端:

| 后端 | 输出片段 |
|---|---|
| CUDA | …完成**蓮條**,有張老師負責 |
| CPU | …完成**臉條**,郵張老師負責 |

**`backend` 进缓存键不是过度设计** —— 不进键就会出现在 A 机器转写、
拷到 B 机器后结果对不上的问题。

#### 模型档位对质量的影响 —— 远超预期

同一段中文语音,只换模型:

| 模型 | 结果 |
|---|---|
| tiny | 神经**往落**、习**体** 3.1、下周**3周** |
| small | 神經**網絡**、**習題** 3.1、下周三**交** ✅ |
| large-v3-turbo(+简体提示) | 神经网络、习题、**下季度排期**、**由张老师负责** ✅✅ |

**结论:CPU 上"能不能用"几乎完全取决于选对模型档位,而不是后端。**
这支持了 §3.3 把"模型自动分档"排在"后端选择"之前的设计。

#### CUDA 编译的三个真实卡点

设计阶段只说"需要自行编译"。实际踩到的:

| 卡点 | 现象 | 解决 |
|---|---|---|
| `nvcc` 不在 PATH | `Could not find nvcc executable` | 显式设 `CUDA_PATH` + `PATH` |
| MSBuild 集成失败 | `The CUDA Toolkit v12.6 directory '' does not exist` | 传 `-DCudaToolkitDir="…\v12.6\\"`(**带结尾反斜杠**) |
| 版本不匹配 | — | 驱动 560.94 只支持到 CUDA 12.6,**装 13.x 会跑不起来** |

最后一条尤其值得记:**`nvidia-smi` 报的 `CUDA Version: 12.6` 是驱动支持的上限**,
不是已安装的版本。装高于它的工具链会"装得上但跑不起来"。

#### 其他实测

| 项 | 实测值 |
|---|---|
| CUDA 推理 | 18 秒音频约 5 秒(含进程启动);显存占用约 1.6GB |
| ffmpeg 解码 | m4a(19 秒,96kbps)→ 正常转写,无需额外配置 |
| 缓存命中 | 同一音频第二次运行,转写阶段直接跳过 |
| 内网可达性 | `huggingface.co` **DNS 被污染**;`hf-mirror.com` 可用(需 `--ssl-no-revoke`) |
| GitHub Release | 可达但不稳定,需要重试与断点续传 |

### 16.3 工具链的坑(与业务无关,但会耗掉大量时间)

| 坑 | 现象 | 根因 |
|---|---|---|
| `can't find crate for 'core'` | 看起来像 Rust 装坏了 | **MSVC 的 `link.exe` 不在 PATH 上** |
| 脚本报"字符串缺少终止符" | 看起来像语法错 | **PowerShell 5.1 按 GBK 读 `.ps1`**,中文注释破坏解析 |
| 文件编码被永久损坏 | 中文变乱码,部分变 `?` | 用 PowerShell 5.1 的 `Get-Content`/`Set-Content` 处理 UTF-8 文件 |
| `Unable to find libclang` | 看起来像依赖或网络问题 | `sherpa-rs-sys` 用 bindgen,需要 `LIBCLANG_PATH` |
| sherpa 原生库下载超时 | 看起来像网络不通 | 构建脚本用 ureq,可从 `SHERPA_LIB_PATH` 复用已编译的库 |

前三条已固化进 `scripts/cargo.ps1` 的注释与附录 B。

### 16.4 仍未完成的部分(诚实清单)

| 项 | 状态 | 补齐方式 |
|---|---|---|
| 说话人区分(sherpa-onnx) | ✅ **已接入并实测跑通** | — |
| 声纹档案的嵌入提取 | 库层完整,**缺提取环节** | 接 sherpa 的 `SpeakerEmbeddingExtractor` |
| 双轨录音(W3) | 未实现 | 见 §13.8,线上会议场景用 `tauri-plugin-system-audio` |

三项"未验证"都不是代码缺口,而是我拿不到的凭据与素材。命令与检查清单见 README。

### 16.5 sherpa 集成的三个实际约束

接入时发现的、设计阶段没预料到的:

**① 嵌入拿不到,缓存对象被迫改变**

见 §16.1 ①。缓存改为说话人时间区间(`diarize_cache` 表),
且**缓存键刻意不含 `DiarizeMode`** —— 用户会反复改人数试效果,
模式进键就等于每次都是一个新条目,缓存形同虚设。

**② 人数配置绑定在初始化里**

sherpa 的 `clustering` 配置是在 `Diarize::new()` 时固定的,`compute()` 时改不了。
所以指定人数时需要**重建实例**。实现里做了这个处理
(`SherpaDiarizer::run` 中 `need_rebuild` 分支),代价是多一次初始化。

**③ 进度回调要求 `Fn` 而不是 `FnMut`**

原生回调签名是 `Fn(i32, i32) -> i32`。要用一个 `FnMut` 闭包就得用 `Mutex` 包一层 ——
这个细节在类型推导报错时不容易一眼看出。

### 16.6 构建可持续性

开发过程中为了验证 sherpa 集成,原生库是通过 `SHERPA_LIB_PATH` 指向临时编译目录的。
这不可持续 —— 那个目录属于中间产物,会被清理掉。

**最终的安排:**

| 内容 | 位置 | 体积 | 说明 |
|---|---|---|---|
| sherpa 原生库(必需部分) | `native/sherpa-rs/` | 14.5 MB | 固化进项目,构建自包含 |
| 完整编译产物 | `%LOCALAPPDATA%\sherpa-rs\` | 约 700 MB | cargo 缓存,不删则不需联网 |
| whisper.cpp 二进制 | `binaries/cpu/` `binaries/cuda/` | 1.2 GB | 含 CUDA 运行时 |
| 模型 | `models/` | 2.3 GB | 4 个 whisper 档位 + 2 个声纹模型 |

**清理后仓库 3.4 GB**(从 16.7 GB),`target/` 与中间产物全部删除,
可从源码重建。重建耗时约 6~10 分钟(其中 sherpa 原生库若缓存仍在则很快)。

### 16.7 一句话总结

**除三件需要真实凭据/素材的验收外,设计文档里的 W1/W2/W4/W6 都已实现并自证。
W3(双轨录音)未实现,因为它是唯一需要实际录制会议才能验证的部分。**

## 17. 工程制(§16 之后的改版)

> 本章记录一次**面向用户的重构**:把"按哈希打散存储"改成"每次录音建一个工程"。

### 17.1 为什么要改

原来的存储是**按内容哈希打散**的:

```text
store/transcript/ab/ab3f9c...json
store/summary/ab/ab3f9c...md
store/speaker_labels/ab/ab3f9c...json
```

这么设计有实在的理由:两台设备录到同一节课只存一份;而且不需要列目录
(路径就是哈希,直接 PROPFIND 那一个路径)。**但它不是给人看的。**

结果就是用户处理完一节课,得到的是几份散落在哈希目录里的文件 ——
没法"打包发给同学",也没法一眼看出这一节课都有什么。

**工程制是面向用户的视图:**

```text
store/projects/2026-09-11_高等数学第12讲/
├─ project.json          元数据(产物清单 / 场景 / 模型 / 后端)
├─ audio/recording.wav   录音副本 —— 工程自包含
├─ transcript.md         带时间戳的转写(对话体)
├─ transcript.json       结构化段落(给程序用)
├─ transcript.srt        字幕
├─ summary-detailed.md   详细总结
├─ summary-brief.md      简略总结
├─ mindmap.mmd           思维导图(Mermaid 源码)
└─ mindmap-outline.md    文本大纲(降级备份)
```

**整个目录可以直接打包发给别人,也能被 WebDAV 原样同步。**

### 17.2 两套存储并存,不是替代

| | 哈希存储 | 工程目录 |
|---|---|---|
| 面向 | 程序(去重与缓存) | 人(阅读与打包) |
| 路径 | 内容哈希分片 | 日期 + 标题 |
| 用途 | 保证同一音频不重复转写 | 可打包、可同步、可阅读 |
| 音频 | 不复制,只记原路径 | **复制一份,自包含** |

**关键设计:工程的 `id` 就是音频内容哈希。**

于是"同一节课录两次"会落到同一个工程,不会每次生成新目录;
而哈希存储那份仍然负责去重与缓存。两者通过 `id` 对齐,不需要额外同步。

### 17.3 两份总结的分工:不是压缩,是换目标

最初的设想是"详细版 + 它的压缩版"。实际做法不同 —— 因为**压缩版没有独立价值**:
用户要短的,直接看详细版的摘要就行。

所以简略版**换了目标**:

| | 详细总结 | 简略总结 |
|---|---|---|
| 给谁看 | 要复习 / 要执行的人 | 只想回忆讲了什么的人 |
| 结构 | 知识点 / 例题 / 待办 / 复习提纲 | 一句话 + 5~8 条要点 + 待办 |
| 长度 | 不限 | **400 字以内**(提示词硬约束) |
| 提示词 | `scene_structure()` | `brief_structure()` + `BRIEF_RULES` |

`BRIEF_RULES` 里明确写了:

> **这是速览,不是详细纪要。** 每条只写结论,不要展开解释。

两者各自的 map-reduce 聚合提示也不同(`reduce_prompt` vs `brief_reduce_prompt`)——
否则简略版会被聚合成一份"短的详细版",失去意义。

### 17.4 思维导图:为什么用 Mermaid,以及它的真实风险

**用 Mermaid 文本而不是生成图片**,理由:

- LLM 生成结构化文本比生成图片可靠得多(后者要另一条图像模型链路)
- 文本可版本控制、可手改、可 diff
- 界面里能渲染成可缩放的矢量图
- 导出 PNG 只需"SVG → canvas",不需要任何图像处理库

#### ⚠️ 真实风险:LLM 生成的 Mermaid 经常有小语法错

实测抓到的第一个错误是**根节点缺 ID**:

```mermaid
mindmap
  ((神经网络基本原理))     ← 非法
```

查 [Mermaid 官方语法](https://mermaid.js.org/syntax/mindmap.html)确认:

> When specifying a shape for a node the syntax is similar to flowchart nodes,
> **with an id followed by the shape definition**

即 `id((文本))` 是必须的(无形状的节点才能直接写文本)。
而 LLM 更习惯 `Root` 那种无形状写法,于是漏掉 ID。

**处理方式是自动修复,而不是报错:**

```rust
pub fn repair_mermaid(src: &str) -> String
```

给缺 ID 的形状节点补 `n1` / `n2` 这样的占位 ID(ID 不显示在图上)。
与其让用户看到一张渲染失败的红框,不如先修再报 ——
同时 UI 会说明"已自动修复 N 处语法问题"。

配套的三道防线:

| 层次 | 手段 |
|---|---|
| 事前 | 提示词里把语法规则写死(禁止括号/冒号/引号) |
| 事中 | `check_mermaid()` 自检 + `repair_mermaid()` 自动修复 |
| 事后 | 渲染失败时降级显示 `mindmap-outline.md` 文本大纲 |

**降级产物是刻意保留的** —— 图渲染不出来时,用户仍然有一份可读的层次结构。
`mermaid_to_outline()` 负责把 Mermaid 转成缩进大纲,包括剥掉 `((形状))`
和节点 ID(`- n1(二叉树的遍历)` 显然不如 `- 二叉树的遍历`)。

### 17.5 同步适配

工程目录纳入同步范围。**同步什么、往哪边传、删不删,是三个独立维度。**

#### 四个维度

| 维度 | 类型 | 回答的问题 |
|---|---|---|
| **方向** | `Direction` | 数据往哪边流 |
| 范围 | `Scope` | 哪些文件**参与**同步 |
| 音频 | `AudioPolicy` | 录音要不要算进来 |
| 删除 | `DeletionPolicy` | 本地没了要不要**删云端** |

外加一个**逐项排除列表** `user_excludes`(界面上勾掉的精确路径)。

这套设计容易混的地方在于"同步什么""往哪边传""删不删"是三件事。
拆开之后常见需求都能表达:

- "只同步这学期的课" → `Scope::Projects`
- "换了新电脑,先把云端拉下来" → `Direction::DownloadOnly`
- "云端是备份,本地是唯一真相" → `Direction::UploadOnly`
- "这个工程的录音别传" → `exclude_path("projects/X/audio")`
- "本地删了云端也别删" → `DeletionPolicy::Keep`

#### 为什么把方向从 AudioPolicy 里拆出来

早期版本 `AudioPolicy` 有 `UploadOnly` / `TwoWay` 两个变体,
和新的全局方向**会打架** —— 能配出"音频只上传 + 全局只下载"这种
自相矛盾的组合。

重整后两个维度正交:

```rust
pub enum Direction { Both, UploadOnly, DownloadOnly }
pub enum AudioPolicy { Sync, Skip }        // 只管"参不参与"
```

任意组合都有明确含义。旧配置的 `audio: upload` / `audio: two-way`
会映射到 `Sync`,不会报错。

#### 方向只限制传输,不改变判定

反方向的差异**既不传输也不删除**。"只上传"时云端多出来的东西保持原样;
"只下载"时本地多出来的东西保持原样,而且**不会删云端**
(删云端是明确的反向操作)。实测:

| `--direction` | 待上传 | 待删除 |
|---|---|---|
| `both` | 3 | 1 |
| `upload` | 3 | 1 |
| `download` | **0**(降级为跳过) | **0** |

#### 范围

```rust
pub enum Scope {
    All,
    Patterns { include: Vec<String>, exclude: Vec<String> },
    Projects { ids: Vec<String> },
}
```

工程选择器支持完整目录名、标题前缀、完整日期 `YYYY-MM-DD`。
**半个日期不匹配** —— 打错了就该什么都不匹配。

通配符自己实现(不引 glob crate):`*` 跨 `/`,`?` 不跨,大小写敏感,排除优先。

#### 逐项排除:取消勾选 ≠ 删除

界面上勾掉一个文件或文件夹时走 `user_excludes`。语义是"**不同步**":

- 不上传、不下载
- **云端副本保留不动**
- 本地文件也不删

这条区分是刻意的 —— 如果取消勾选等于删云端,这个开关就没人敢点了。
要清理云端必须走删除策略那条路(本地删掉 + 策略允许)。

`include_path` 恢复勾选时会**同时清掉子项的排除**,否则用户会困惑
"为什么取消父目录再勾回来,还有个文件没同步"。

#### 安全删除

删除不是"本地没了就删云端"。判定要**四个条件同时成立**:

1. manifest 里有记录,且不是墓碑
2. 本地确实没有
3. **这条记录是本机写的**(`origin` = 本机设备 ID)
4. 在范围内 + 策略允许 + 方向允许上传

第 3 条防止误删:别的设备上传、本机还没下载的文件不会被当成"本地删了"。

manifest 为此加了 `origin` 与 `deleted_at`(墓碑)。墓碑的作用:
直接删记录的话,另一台设备会看到"本地有、manifest 里没有",
判定成"远端没有 → 上传",把刚删的文件又传回去。

`origin` 为空(旧记录、`rebuild_manifest` 扫出来的)一律按"不是本机"处理 ——
**保守,不删**。

#### 本地状态表(界面用)

manifest 记录的是"**远端有什么**",回答不了"这个文件传上去了吗"。
所以另有一份 `store/sync-state.json`,**只在本地,不参与同步**:

```rust
pub struct SyncState { files: BTreeMap<String, FileSyncRecord> }
pub struct FileSyncRecord { last_synced_at: Option<i64>, etag: Option<String>, size: Option<u64> }
```

`last_synced_at` 是关键:它让"**从未同步过**"和"**同步过但现在不在范围内**"
能区分开。没有它,用户勾掉一个文件后就无从判断它到底传没传过。

八种显示状态:

| 状态 | 符号 | 含义 |
|---|---|---|
| `Synced` | ✓ | 已同步 |
| `PendingUpload` | ↑ | 待上传 |
| `PendingDownload` | ↓ | 待下载 |
| `PendingDelete` | ✗ | 待删除云端 |
| `Excluded` | — | 未同步(用户勾掉的) |
| `NeverSynced` | · | 从未同步 |
| `DeletedLocalKeptRemote` | ◌ | 本地已删(云端保留) |
| `Conflict` | ! | 需处理 |

#### 清单树(界面结构)

`build_inventory()` 生成三层树:**工程 → 分组 → 文件**。

```text
2026-09-11_高数            [✓ 已同步]
  简略总结                 [✓ 已同步]
    summary-brief.md       [✓ 已同步]
  详细总结                 [✓ 已同步]
    summary-detailed.md    [✓ 已同步]
  思维导图                 [✓ 已同步]
    mindmap.mmd            [✓ 已同步]
  转写                     [✓ 已同步]
  录音                     [— 未同步]     ← 组级勾选
    recording.wav          [— 未同步]
  元数据                   [✓ 已同步]
```

**为什么不把文件全铺开:** 一个工程近十个文件,十个工程上百行。
按类型分组后,"这个工程的录音别同步"变成一次点击。

两个实现要点:

1. **聚合状态取"最需要注意的"子状态** ——
   全同步的文件夹里藏着一个没上传的文件,文件夹也该显示"待上传"。
   优先级:需处理 > 待删除 > 待下载 > 待上传 > 未同步 > 本地已删 > 从未同步 > 已同步

2. **本地已删除的文件也要列出** —— 只遍历本地文件的话,
   "本地删了、云端那份还在"的文件根本不出现在清单里,
   而那恰恰是用户最需要看见的。所以要把状态表里的条目也补进来,
   并标记 `local_exists: false`。

#### 远端目录与完整地址

配置由两段组成:

```text
base_url    https://cloud.example.com/seafdav     服务地址
remote_dir  recording_summary                   远端目录(可多级)
────────────────────────────────────────────────────────────
root()      https://cloud.example.com/seafdav/recording_summary
```

`remote_dir` 支持多级,例如 `recording_summary/2026秋`。
`root()` 会**过滤空路径段并 trim 每段** —— 用户把地址填成 `.../seafdav/`
再给一个 ` /recording_summary/ `,两侧斜杠叠加会拼出 `//`(有些服务器 404),
前后空格更会让 MKCOL 失败。

##### 自动拆分完整地址

用户脑子里想的是**一条完整地址**:

```text
https://cloud.example.com/seafdav/recording_summary
```

而不是"服务地址"+"远端目录"两个框。直接粘进第一个框会拼出
`.../seafdav/recording_summary/recording_summary`,而报错是 404,
完全指不到问题所在。

所以 `split_webdav_url()` 会把它拆开:

```rust
split_webdav_url("https://cloud.example.com/seafdav/recording_summary")
// → Some(("https://cloud.example.com/seafdav", "recording_summary"))
```

切分规则:

1. 路径含**已知服务根**(`/seafdav`、`/remote.php/dav`、`/dav` 等)→ 从它之后切
2. 否则路径有 2 段以上 → 取最后一段当子目录
3. 路径只有一段或没有 → `None`(本来就是服务地址)

规则 1 比"取最后一段"可靠,因为服务根名不可能是用户建的目录。
规则 2 是给未知服务的兜底。规则 3 保证**幂等** ——
拆好的服务地址再拆一次仍是 `None`,不会把 `seafdav` 当成目录。

CLI 与 GUI 都接了:CLI 在 `sync login --url` 里拆,GUI 在保存配置时拆,
并把"已从地址里识别出远端目录:xxx"显示出来让用户知道。

有一条测试守着"拆完再拼回来必须还是原来的地址" ——
否则用户会以为程序改错了:

```rust
let (base, dir) = split_webdav_url(url).unwrap();
assert_eq!(cfg_with(base, dir).root(), url);
```

##### ⚠️ 上传前必须先建父目录

WebDAV 的 PUT **不会自动创建中间目录**。往 `transcript/ab/x.json` 上传时,
如果 `transcript/ab/` 不存在,Seafile 返回 **409 Conflict**。

`WebDavClient::ensure_parent_dir()` 负责逐级 MKCOL:

```text
a/b/c.md  →  MKCOL a  →  MKCOL a/b  →  PUT a/b/c.md.part  →  MOVE → a/b/c.md
```

（`405 Method Not Allowed` = 已存在,视为成功。）

**这个调用曾经漏掉了** —— `ensure_dir` 写好了却没人调,是死代码,
所以单元测试也照不出来(测试不碰真实服务器)。首次连接真实云盘就会暴露。
现在 `put_atomic` 开头第一件事就是建父目录,并加了测试明确列出
所有需要父目录的实际路径形态。

#### 性能取舍:`probe` 参数

`get_sync_inventory(probe)` 有两种模式:

| `probe` | 行为 | 耗时 |
|---|---|---|
| `false`(首屏) | 只按本地 + 状态表推断 | 秒开 |
| `true`(点「核实云端状态」) | 为每个文件发 HEAD 请求 | 上百文件十几秒 |

打开页面用 `false`,用户主动点按钮才跑 `true`,日常使用不卡。
没配 WebDAV 账号时自动降级为 `false`(无法联网)。

### 17.8 实现时踩到的一个非预期 bug

新工程视图的标签页**被旧的历史详情页选择器破坏**:

```js
// 旧「历史记录」详情页
document.querySelectorAll('.tab')       // ← 匹配所有 .tab,包括工程的
document.querySelectorAll('.tabpane')   // ← 同理
```

点工程标签页时**两个处理器都触发**:工程的处理器刚把 `active` 加到
`ppane-mindmap`,旧的处理器立刻把所有 `.tabpane` 的 `active` 全清掉
(因为 `ppane-mindmap !== pane-undefined`),界面变成一片空白。

**修法是把旧选择器限定到 `#view-detail`。** 教训:同一个页面里有多个
"标签页"组件时,选择器必须带作用域。

### 17.9 前端依赖:bundle 还是 CDN

mermaid 的 UMD 包 **5.4 MB**。选择**内嵌到 `ui/vendor/`** 而不是用 CDN ——
这是桌面应用,必须离线可用。

代价是它不进版本库(体积大),需要手动下载一次。所以:

- `ui/vendor/README.txt` 记录了下载地址与校验方式(优先用 npmmirror 国内镜像)
- `.gitignore` 排除该文件但保留 README
- 设置页有依赖检查,**缺库时明确告知**而不是让用户看到一片空白
